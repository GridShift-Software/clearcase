# GRS-102: cf and Void for the alpha agent tooling jobs

Addendum to [GRS-102](https://linear.app/vaper/issue/GRS-102). It adds to GRS-100 (`docs/research/grs-100-hosted-software-audit.md` at `5e1ceae`, Void subsection) and GRS-101 (`docs/research/grs-101-local-agent-test-platform.md` at `2f810e9`, local Workers capabilities) and repeats neither. Base `b93bad097fdd`. Sources were read on 15 October 2026. Labels: **[F]** documented fact; **[S]** read in published package source, not executed; **[I]** inference; **[R]** recommendation; **[U]** unknown; **UNRUN** no execution evidence. **UNSUPPORTED** is reserved for an explicit documented or source-level rejection. Absence from the pages and source searched is written "not found", which is not a claim that the capability is missing.

Nothing was installed, executed (no `npx` or `bunx`), migrated, logged in, provisioned or deployed. Four tarballs (`cf-1.0.0-beta.17`, `void-1.1.11`, `adapter-cloudflare-8.0.1`, `vitest-plugin-1.4.3`) were downloaded to a scratch directory and read as text. Source findings describe those released versions only, not unreleased `main`. No item below is a runtime PASS; every proof in [Proof matrix](#proof-matrix-all-unrun) is UNRUN.

## Verdict

1. **cf is a good first choice for discovery, account and resource tasks, dry runs, version uploads and traffic splits [F][R][C1].** Use it in a supported Node process. Commands that do not build (resource, schema, search) do not trigger automatic configuration. Commands that build, run in a Wrangler project that has no `cloudflare.config.ts`, write a new config that ignores the Wrangler one [C4].
2. **cf's refusal covers one path only: automatic framework setup for SvelteKit [S].** In beta.17 the SvelteKit entry has `supportsCf: false`, and automatic configuration throws "cf does not support SvelteKit projects yet" [C13]. Automatic configuration is skipped when `cloudflare.config.ts` exists or `--prebuilt` is passed [F][S]. Whether cf can then build and deploy Kit 3 is **[U]**, because cf reads Build Output and Kit 3 with adapter 8 is not shown to write it (P2). Section [Trace](#trace-kit-3-through-automatic-setup-explicit-config-and-void) has the three paths.
3. **Void's direct-Cloudflare mode (`void deploy --platform cloudflare`) has a source-level route for Kit 3 [S].** It runs `vite build`, bundles the adapter's `_worker.js` itself and uploads with `cf deploy --prebuilt`, so cf's SvelteKit refusal is not on its path [S][C13]. The adapter imports `wrangler` as a library, which does not stop Void or cf from being the top-level tool. Void is not proven to work for this app (P6, P10).
4. **Native D1 without Drizzle imports is not blocked at source level [S].** Void's deploy-time Drizzle checks end early when there is no Drizzle schema, no `meta/_journal.json` and no Void auth. Its optional `void db` commands are not needed to build or deploy. This is source-only and UNRUN (P6).
5. **Wrangler 4.151.0 remains the fallback** where neither tool is shown to work: live logs, single-secret writes, `rollback`, and the Workers Vitest integration and `createTestHarness`, which depend on Wrangler and its config file [W1][W2][W5].
6. **Treat the cf beta as moving [F].** Eighteen betas (beta.0 to beta.17) shipped between 25 September and 14 October 2026 [C12]. beta.15 and beta.16 broke behaviour: destructive exit codes changed, and 42 commands were renamed [C11]. Pin exact versions and re-read the release notes before each bump [R].

## Release state, runtimes, licences

- **cf** `1.0.0-beta.17` (npm `latest`, published 14 October 2026) is tagged `cf@1.0.0-beta.17` at commit `a3c9939a5b41` [C11][C12]. All source findings here are from that tarball. `main` was 7 commits ahead at `00b7d2a8c593` on 15 October: one changeset bumping two internal packages, plus Renovate and Forge plumbing [C11]. That commit list was read, not the code, so `main` is untested.
  - npm versions 0.0.1 to 0.0.3 of `cf` (2013) are an unrelated config loader, so pin `cf` to an exact `1.0.0-beta.N` [C12][R].
  - Licence: npm declares `MIT OR Apache-2.0` and the tarball ships both licence files. GitHub's detector reports Apache-2.0 [C11][C12].
  - Runtime: the bin uses `#!/usr/bin/env node`; `engines.node` is `>=22` [C13]. The docs require Node 22.18 or later: "Bun is not supported. When `cf` runs on Bun, commands that load `cloudflare.config.ts` fail" [C2][C5].
  - Engine: `miniflare` 5.20261012.0-beta pins `workerd` 1.20261012.1 (Apache-2.0) [C12].
- **cf delegates and does not bundle [F][C4].** `cf dev` and `cf build` run the framework command, the Cloudflare Vite plugin 2.0 beta (`2.0.0-beta.v.0`, published 15 October 2026, no Wrangler dependency), or Wrangler 4.136.0 or later. cf does not run `package.json` scripts.
- **Void** `1.1.11` (MIT, published 15 October 2026) declares `engines.node >=24.21.0` [C12]. - **Wrangler 4.151.0** is `MIT OR Apache-2.0`, needs Node `>=22.0.0`, and uses the same miniflare and workerd pins [C12]. The blog post promises Wrangler maintenance "for 18 months after the beta ends" [C10].
- **Host roles [R]:** Bun 1.4.2 installs packages and keeps app dev, build and tests [C2]. A supported Node process hosts cf, Void, Wrangler, `createTestHarness` and the Vitest plugin; vitest-plugin 1.4.3's source refuses `cloudflare.config.ts` loading under Bun [C13]. ## Trace: Kit 3 through automatic setup, explicit config and Void

- **Path A, automatic setup [S][C4].** It runs from `cf dev`, `build`, `deploy` (including `--dry-run`), `previews deploy`, `workers versions create`, `workers triggers deploy`, `workers check` and `cf init` when no `cloudflare.config.ts` exists. Its SvelteKit class would run `sv add sveltekit-adapter=adapter:cloudflare+cfTarget:workers`. For the `cf` target, `validateFrameworkTargetSupport` throws first. The registered Kit major is 2 (a higher major only warns). Verdict: **UNSUPPORTED**, scoped to this path.
- **Path B, explicit config or prebuilt [F][S].** `getDetailsForAutoConfig` marks the project configured when `cloudflare.config.ts` exists, and the setup run asserts "not configured" before the refusal. The docs also say `--prebuilt` skips it [C4]. `cf build` then runs the detected framework command (probably `vite build` [I]) and reads `.cloudflare/output/v0/`. adapter 8 writes `.svelte-kit/cloudflare/_worker.js` and no Build Output is shown, so build and deploy are **UNRUN/[U]** (P2). `cf migrate` converts Wrangler projects; its docs do not mention SvelteKit [C14]. `cf workers versions create --prebuilt` and `cf deploy --prebuilt` upload any valid Build Output whatever framework made it [F][C4].
- **Path C, Void-generated config [S][V1][V3].** Void uses a root `wrangler.jsonc`, a framework-referenced one, or a `.void-wrangler.jsonc` generated from `void.config.ts` (`wrangler.toml` is rejected). Its SvelteKit preset is `vite build`, output `.svelte-kit/cloudflare`. `prepareCfFrameworkBuildOutput` bundles the Worker and public assets into Build Output, and the upload runs `cf workers versions create --prebuilt` or `cf deploy --prebuilt`. Void also checks that the prebuilt upload cannot create a resource as a side effect. Unrun: P6.
- **Native D1 without Drizzle [S][V4].** Void infers the `DB` binding from `env.DB` or checked-in migrations, with no Drizzle import needed. `hasDeploySchemaDrift` returns false when no Drizzle schema and no Void-generated auth schema exist. `assertJournalCoherence` returns early without a journal (source comment: hand-written `.sql` projects without `db/schema.ts` are supported). The V4 docs' statement that deploy compares a Drizzle schema with `meta/` applies only when a Drizzle schema exists. Void-managed auth is UNSUPPORTED in framework mode [V1].

## Per-client boundary and credentials

Topology: all clients share ONE owned Cloudflare account, with separate Worker, D1, R2, bindings, secrets and Clerk app per client. The account is no boundary [I].

- **Token granularity [F][T1][T2][T4][T5].** Token policies name three resource types: User, Account (one or all) and Zone; R2 adds a Bucket type. Permission groups (Workers Scripts, D1, Workers R2 Storage) are account-level. No Worker-level or D1-level resource type was found. R2 Object Read or Write tokens can be bucket-scoped, but only for the S3 API, not the REST API [T4]. A Worker's D1 and R2 bindings need no token. Account API tokens (`cfat_`, owned by the account) list Workers, D1 and R2 as compatible [T3]. Members can grant only a subset of their own permissions.
- **No per-client control-plane boundary is promised.** A token able to deploy one client's Worker can deploy another's in the same account. Separate configs, directories and `--no-provision` do not stop a wrong existing binding [I]. Config separation is not credential isolation.
- **Recommended boundary [R], enforcement UNRUN.** (1) Hold two account-scoped tokens, never `*` accounts, with a TTL. The deploy token carries Workers Scripts Edit plus read on D1 and R2, which Void's docs say a deploy needs [V3]. A separate provisioning/migration token carries D1 Edit and Workers R2 Storage Edit and is used only in gated steps. Wrangler's "Edit Cloudflare Workers" template adds KV, Routes and R2 write and omits D1 [T6], so build a custom policy instead. cf's own minimum set was not found. (2) Per-client secrets (Clerk keys) are Worker secrets and are never in repo files. (3) Add a reviewed pre-deploy manifest check per client: expected `accountId`, Worker name, D1 name and ID, R2 bucket, KV ids and secret names, compared with the resolved config. It fails on any foreign ID. (4) The deploy process, not the project directory, injects the token for the one client being deployed. Do not put it in `.env` files, `~/.config/cloudflare` profiles or other shared unreviewed local pools. cf lets `CLOUDFLARE_API_TOKEN` beat every profile and reads `.env` from the current directory [C2].
- **cf account and modes [F][C2][C4].** Account order: `CLOUDFLARE_ACCOUNT_ID`, then `accountId` in `cloudflare.config.ts`, then `node_modules/.cache/cloudflare/`. Function-form config "deploys a separate Worker only when it returns a different `name`", and prebuilt output must be deployed with the mode it recorded. Void's direct-Cloudflare mode has no named environments, so a Void client needs its own `void.config.ts` [V3]. Selecting one from a shared source tree was not found. Keep one maintained codebase, with per-client descriptors as data and generated tool config [R].
- **Repository hygiene [R].** The repo `.gitignore` covers `.env*`. It does not cover `.cloudflare/`, `.wrangler/` or `.void/`, and cf does not add `.cloudflare/` [C9]. Agents run with `DO_NOT_TRACK=1` and `CLOUDFLARE_DEPENDENCIES_INSTRUMENTATION=false`, because cf records search queries and uploads dependency metadata by default [C8][C11]. A Void telemetry switch was not found.

## Local simulation, remote work, cost and Void Platform

- **Local [F]** means verified local bindings in `--local` cf commands, Miniflare and workerd dev servers, with remote connections off (`remote` bindings unset), telemetry controlled as above, and no credentials in the environment. Only that combination is network-free and costs nothing (GRS-101) [C3][C4].
- **Remote [F]:** `deploy`, `previews deploy`, version and traffic changes, `d1 time-travel restore`, Void `--remote` and Void `remote` bindings write real data. Some remote resource commands only read; dry runs send no API requests. Workers quotas and any plan limits of the owned account apply, and its plan was not checked. The R2 page says R2 must be purchased before S3 tokens can be generated [T4].
- **Void Platform (`--platform void`) is unadopted, and no cost direction rejects it [R].** Direct-Cloudflare mode has no platform. The self-hosted platform needs Workers for Platforms on a paid plan (the pricing page's example lists a $25.00 monthly subscription plus usage) [B1], R2 and Analytics Engine enabled, an empty PostgreSQL database that Void does not provision and that is billed separately, a login provider, a management and a runtime API token (stored as a Worker secret), and ongoing `platform upgrade` and repair work [V6][V7]. It buys managed projects and encrypted app secrets, but fit with per-client isolation is **[U]**, and the direct mode already covers uploads and traffic. Revisit if the direct mode's missing dry run or environments block the work.
- **Agent hazard [F].** `void db execute --remote` skips its destructive-statement prompt when not on a TTY [V4]. Keep it off agent allowlists [R].

## Remaining unknowns

- Whether Kit 3 with adapter 8 produces Build Output cf accepts (P2), and whether `cf migrate` handles it.
- Void's runtime behaviour for native D1 without Drizzle, including provisioning side effects and a per-client config from one source tree (P6, P9, P10).
- Exit code for unforced destructive commands (P8); cf `--local` state sharing with dev servers (P4); vitest-plugin host (P5).
- Token grant enforcement and cf's minimal permission set. No Worker or D1 resource scoping was found in current docs, so the boundary rests on roles and the manifest check.
- Resolved by source checks: the refusal's scope, Void's cf-prebuilt chain, optional Drizzle checks, token granularities, the helper Node line, and the Platform requirements.
