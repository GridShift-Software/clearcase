# ClearCase planning conventions

The plan applies the installed Matt Pocock and pstack skills to this repository. It also uses Jove's proven coordination pattern. These are planning rules, not claims that the application has passed verification.

## Matt Pocock lens

`ask-matt` routes multi-session work through a spec, dependency-linked tickets and a fresh execution context. The product brief defines scope; `work-items.json` and Linear define the graph; the kickoff starts the next context. Each delivery issue names an observable outcome, not just a technical layer.

`domain-modeling` supplies the glossary. It distinguishes submissions, results packages, candidates, user work, activation and publication. A local backup is not a results import, and upload completion is not publication approval.

`codebase-design` keeps the import/validation and case-view interfaces small. Legacy-format adapters handle actual format differences. V1 does not gain a speculative multi-cloud framework. Storage separation is introduced where local and hosted implementations actually differ.

The installed bundle lacks the `to-spec`, `to-tickets` and `implement-spec` leaf files. Their flow is documented by the installed router, but those missing skills were not executed. No global skill installation or model configuration was changed.

## pstack lens

- Sequence Work into Verifiable Units puts the fixture and package gate before the complete pilot, then unlocks feature work and release gates.
- Separate Before Serializing Shared State gives each writer a worktree and reserved files. Shared configuration and integration have one owner.
- Prove It Works requires real browser/file evidence and an independent reviewer at each gate. HOLD and skipped checks do not count as PASS.
- Build the Lever supplies a rerunnable checker and generated ticket/plan views, so coverage and dependency consistency can be verified without rereading the conversation.
- Guard the Context Window delegates Jove exploration and independent review while keeping the canonical plan in files.

The detailed V1 plan follows the multi-phase checklist structure. Its ten live scenarios per implementation unit are run within the concurrency cap. Decision and acceptance-gate issues use evidence appropriate to their output. The later V2 roadmap is deliberately refined at its decision gate before code dispatch; it does not pretend hosting and role decisions are settled.

T3's task and preview tools replace Cursor-specific commands. The remote is `origin`, GitHub `GridShift-Software/clearcase`, with stacked feature PRs into `dev`, linked with `gh stack link` and updated by merging rather than by pstack's `gt` restacks; pstack's available `orch` CLI is not used for this run. The plan records these differences instead of inventing those capabilities. No ten-agent cloud fleet, automatic merge loop or schedule starts during planning.

## Open decisions remain explicit

The current hosted operator endpoint is unverified and has its own discovery issue. It does not block local implementation. V2 may use the new results contract if the legacy route remains inaccessible, with that migration choice recorded at the hosted design gate.
