# Developing the local ClearCase app

The local pilot (GRS-12, CC-03): an operator imports a results package for a case folder, reads its validation report, previews and activates it, and follows a citation from the chronology or overview to the original, which opens safely or downloads. This page is the developer contract for the app and for the M2 view owners who extend it. The package contract is [results-package.md](results-package.md); words follow [GLOSSARY.md](../GLOSSARY.md).

## Stack decision

SvelteKit 3 (3.1.0 since GRS-112; the stack judge below ran on Kit 2) with TypeScript, `node:sqlite` storage, run and built with Bun 1.4.2.

Historical stack-judge evidence lives in the workspace's `../spikes/stack-judge/`, outside this repository and Git. Three stacks used the same scenarios. Scores out of 10:

| Stack | Score | Storage |
| --- | --: | --- |
| SvelteKit 2.70.3 + `node:sqlite` | 8.7 | two SQLite files: immutable results, precious user work |
| SvelteKit 2.70.3 + plain files | 8.1 | JSON files per version; whole versions held in memory |
| Vite SPA + Hono + plain files | 6.7 | JSONL without fsync; stopped on a torn tail |

All three met every budget by a wide margin, so no measured constraint justifies leaving the planned SvelteKit and TypeScript. The minimum viable storage choices were plain files and SQLite; SQLite won on crash safety with explicit pragmas, bounded memory, chronology speed and a clean split between rebuildable results and user work. The hardened prototype lives in the workspace's `../spikes/pilot-hardened/`, outside this repository and Git. This app ports that Bun prototype onto GRS-10's package library. The Bun requirement is the user's (8 October 2026), recorded in `AGENTS.md`.

## Toolchain and commands

Exact pins are in `package.json` (`packageManager: bun@1.4.2`); the lock is `bun.lock`. Install once with `bun install --frozen-lockfile`, then run every script with `bun run --bun <script>`:

| Script | What it does |
| --- | --- |
| `gate` | `scripts/gate.mjs`, the one command that runs the checks: `build`, `check`, `test --maxWorkers=2`, `test:e2e`, `parity --all --strict-register` and `verify:pilot:v5`, stopping at the first failure. It prints at most 30 lines (the head SHA and whether the tree is dirty, the browser lock, a PASS/FAIL/SKIP line per step with seconds, the tail of the first failure's log, then `GATE PASS <sha>` or `GATE FAIL <step> <sha>`) and writes full logs to `.local/gate/<step>.log`, with `:` in the step name replaced by `-` (`test-e2e.log`). Before the first step it checks every step's prerequisites. The v5 steps need `.local/v5-verification.json`, the case folder it names, and an accepted resultsVersion that this revision's converter still produces: the gate converts the sample (about 3 s) and compares. A missing or stale prerequisite fails its step before anything runs (`FAIL parity prerequisite (no step ran)`), and the message names the expected resultsVersion and how to refresh the locator. The gate refuses to start (`GATE FAIL env`) when `E2E_ONLY`, `E2E_STOP_AFTER`, `E2E_LATENCY_SIZES_MIB`, `CLEARCASE_E2E_TMP` or `PARITY_MAX_COMBOS` is set, and after `test:e2e`, `parity` and `verify:pilot:v5` it requires the summary that step wrote in this run (under `.local/gate/`) to say `evidence: true` for HEAD; a missing, stale or `evidence: false` summary fails the step. The three browser steps run through the browser lock the gate admits ([Browser admission](#browser-admission-grs-154)); without admission the gate fails `GATE FAIL env` before any step. After the last step it reads HEAD and the tree again and fails `GATE FAIL head` when the tree was dirty at entry or is dirty now, or HEAD moved: a gate passes only for the clean commit its first line names. The gate runs in a process group of its own and records it in `.local/gate/pid`; `bun run --bun gate --stop` stops that group (SIGTERM, then SIGKILL after 15 s) and nothing else, including a group whose leader was SIGKILLed: its members are recognised by the `CLEARCASE_GATE_LEADER` variable that names this worktree. It exits non-zero when something still runs afterwards. A second gate in the same worktree fails with `GATE FAIL busy`, also while such orphans run. Admission is an exclusive `flock(2)` on `.local/gate/pid.lock`, taken before any work starts and held by the kernel until the gate exits or dies, so of several gates started at the same moment exactly one runs, and a gate that died leaves nothing to recover: the next one replaces its record. Each problem is one `path:line:col: error [rule] message` line |
| `build` | `vite build` (adapter-node) into `build/`, then `scripts/pilot/copy-pdfjs.ts` bundles pdf.js and the viewer into `build/pdfjs/` and stamps `build/clearcase-build.json` with the source revision; it also replaces adapter-node's `build/index.js` with a stub that exits 1, because that entry would listen on every interface (HOST unset) without the exact-Host check |
| `test` | Vitest: GRS-10's package suite and the pilot's unit tests (`src/lib/**/*.test.ts`); run it offline as `unshare -rn env OUTER_UID="$(id -u)" OUTER_GID="$(id -g)" tests/e2e/pilot/offline.sh bun run --bun test` |
| `test:e2e` | `tests/e2e/pilot/run.mjs`: the browser and durability suites against `./build`, each in its own network namespace, then the loopback bind check |
| `verify:pilot:v5` | the ten lanes on the real v5 sample, configured by the ignored `.local/v5-verification.json`, writing `lane-NN.txt` and `.png` to `$CLEARCASE_REPORT_DIR` |
| `measure` | `--ticket CC-NN --baseline REV --candidate REV`: `CC-02` runs GRS-10's measurement unchanged, `CC-03` measures the pilot budgets, and any other `CC-NN` runs `scripts/measure/ccNN.mjs` when it exists (CC-06 and CC-08 do). Without a known ticket it prints the usage and exits 2 |

### Browser admission (GRS-154)

Browser jobs share the host's two browser slots through the workspace's `orch-bin/browser-lock` (`--exclusive` takes both, for evidence runs). The local `gate`, `scripts/verify/evidence.sh` and the hosted runner (`verify-clearcase-hosted` and `gate:hosted` through its preflight) resolve the lock with one contract, `scripts/browser-lock.mjs`, in this order:

1. `BROWSER_LOCK` set, even empty: refused. It is the retired spelling of `CLEARCASE_BROWSER_LOCK`, so an old export fails loudly instead of meaning anything.
2. `CLEARCASE_BROWSER_LOCK=none`: browser jobs run without a slot. This is the deliberate bypass for a host with no workspace lock, such as CI's `gate-hosted` step. Use it nowhere that shares the workspace's browsers.
3. `CLEARCASE_BROWSER_LOCK` set to the absolute path of an executable file: that command takes the slot.
4. `CLEARCASE_BROWSER_LOCK` set to anything else, empty or relative included: refused.
5. Unset: `orch-bin/browser-lock` in the directory above the repository's `git rev-parse --git-common-dir` (`<workspace>/clearcase/.git`), so the main checkout and every linked worktree under `worktrees/` find the same lock. Refused when that file is missing or not executable.

A refusal stops the entry point before it runs anything: `gate` prints `GATE FAIL env`, `evidence.sh` exits 2, the skill's preflight exits 3 and `gate:hosted` prints `GATE FAIL preflight`. `bun scripts/browser-lock.mjs` prints the lock this checkout resolves (an empty line for none) and what admitted it.

## Hosted runtime (GRS-112)

One app builds two artifacts, chosen by one build variable. Unset (or `local`), `CLEARCASE_TARGET` builds the local pilot on adapter-node, which `bun run --bun start` serves. `CLEARCASE_TARGET=hosted` builds the Workers artifact on adapter-cloudflare from the route tree and server hooks that `deploy/client/hosted-files.json` selects (`deploy/client/routes/`, `src/lib/server/runtime/hosted/hooks.server.ts`). Set it only through `build:hosted`. The CSP and the Origin check are the app's, and the hosted graph has its own `handleError` (`src/lib/server/runtime/hosted/handle.ts`) in place of the local one; in the hosted graph the identity handle's authorization replaces the local loopback boundary. The pins are those of `docs/acceptance/hosting/runtime.md` (Kit 3.1.0, adapter-cloudflare 8.0.1, Wrangler 4.151.1, workerd 1.20261012.1).

The second variable, `CLEARCASE_HOSTED_PROFILE`, is a test variable read at build time. `production`, the default, holds no test double. Every protected request is refused with 503 until the identity, storage (GRS-117) and asset (GRS-118) adapters land. `/health` and the 404 for `/api/browse` still answer. `hosted-gate` swaps in `src/lib/server/runtime/hosted/gate/hooks.server.ts` and the named test doubles under that directory. The import guard and the artifact scan refuse those doubles in any production artifact.

| Command | Host | What it does |
| --- | --- | --- |
| `bun run --bun build:hosted` | Bun (the build and the script) | `vite build` with a credential-free environment allowlist into `.svelte-kit/cloudflare` and `.svelte-kit/output/server`. Stamps the artifact with HEAD (Kit `version.name`, and the build stamp `/health` reports), scans the emitted modules (`scripts/ci/hosted-artifact.ts`), records the stamp and artifact digest in `.svelte-kit/clearcase-hosted.json`, then regenerates the local tree's Kit types |
| `bun run --bun start:hosted` | Node hosts Wrangler only, and Wrangler runs native workerd, which serves the artifact | Refuses a dirty tree, a stamp that is not HEAD, a dirty-built stamp or a changed artifact. Provisions local D1 and R2 under `.local/hosted/run-*/persist` with `wrangler d1 execute --local` and `wrangler r2 object put --local` (the runtime sentinels, plus the synthetic two-client fixture for `hosted-gate`). Then it serves `http://127.0.0.1:$PORT` (41301) through `wrangler dev --local` with GRS-106's environment allowlist (fresh HOME and XDG, no telemetry, error reports, cf.json fetch, dotenv or process env). It checks `/health` reports this artifact on workerd and records `.local/hosted/server-$PORT.json`. `--stop` (same `PORT`) stops that server and its process tree |
| `bun run --bun test:hosted` | Bun sends every request; workerd answers | Against the running server, at HEAD: the request, render and action smoke legs of `tests/hosted-foundation/runtime/smoke.ts`, then the import-boundary negative test (`guard-mutations.ts`). Writes `.local/hosted/test-<sha>-<profile>.json` and exits 0 only when every leg passes |

A Node or Bun server pass is not hosted evidence; only these workerd runs are. No Cloudflare account, token, login or deploy is involved: every binding in `deploy/client/wrangler.toml` is `remote = false`, and its database id is a placeholder. The client a deployment serves comes from its `CLEARCASE_CLIENT_ID` var, never from a request.

### Test doubles and the GRS-138 feature map

- **Doubles.** In the hosted-gate artifact these are doubles:
  - identity: a test identity, sessions in local D1, with no Clerk;
  - store: case identity and publication state in local D1 fixture tables (results stay unavailable until GRS-117 and GRS-118 land);
  - assets: originals in local R2, read whole and checked against the recorded size and SHA-256 before release, with the audit event written first;
  - audit: events in local D1.

  User work is unavailable. The D1 and R2 bindings and workerd themselves are real local Miniflare/workerd, not Cloudflare's.
- **Memory doubles.** The memory doubles (`src/lib/server/runtime/memory*.ts`) serve the unit tests in `tests/hosted-foundation/runtime/` only. No artifact contains them.
- **Fixture.** `tests/hosted-foundation/runtime/gate-fixture.ts` defines it:
  - two clients, A and B;
  - cases A1 (no publication), A2 (withdrawn) and B1;
  - identities `a-viewer` (A1), `a-editor` (A1 and A2), `a-unassigned` and `b-editor` (B1);
  - four synthetic originals.

  The local deployment serves client A, so to it B's session is wrong-client, and B's case and asset ids do not exist.

The feature map GRS-138 drives (the smoke test walks the same steps):

```sh
CLEARCASE_HOSTED_PROFILE=hosted-gate bun run --bun build:hosted
bun run --bun start:hosted &        # http://127.0.0.1:41301
bun run --bun test:hosted
bun run --bun start:hosted --stop
```

A verification run stops only a server it started: when a server already holds the port (`server-$PORT.json`), the run refuses to start and leaves that server, its PID file and its state alone.

1. Sign in as the test identity. On `GET /sign-in` (`[data-auth-provider=double]`), choose `client-a/a-viewer` in `#test-identity` and submit `#sign-in`. The form answers 303 to `/cases` with an HttpOnly `clearcase_session` cookie.
2. Open the provisioned case. On `/cases` (`[data-auth-state=signed-in]`), follow `a[data-action=open-case][data-case-id=case-a1]`. `/cases/case-a1` shows `[data-results-state=pending]` (`ResultsState`), the originals, and `[data-user-work-state]` apart from results.
3. Open an original. `a[data-action=open-original][data-asset-id=a1-letter]` serves `/cases/case-a1/originals/a1-letter`: 200, the whole file, `attachment`, audited. A `Range` request gets 416.
4. Deny a wrong-client request. Sign in as `client-b/b-editor`: `/cases` answers 401 `[data-denial-code=wrong-client]`, and B's original answers 401 with no bytes. As `a-viewer`, `/cases/case-a2`, `/cases/case-b1` and `/cases/case-a1/originals/b1-letter` answer 404.

   Each denial and delivery is a row in local D1's `audit_event`. Read it with `wrangler d1 execute DB --local --persist-to <run>/persist --config deploy/client/wrangler.toml --command "SELECT * FROM audit_event"`.

### Import boundary

`bun run --bun check:hosted-imports`, run by `check`, walks both profiles' source graphs before tree shaking; each hosted build (`vite.config.ts`, at `buildStart`) walks only its own profile's graph. Every route file Kit builds is a root (`+page`, `+layout`, `+server`, `+error`, their `@` layout-reset and `.server` forms), any other `+`-prefixed file under the routes fails closed, and the guard resolves the following:

- TypeScript aliases;
- re-exports;
- literal dynamic imports;
- Svelte components (compiled, script blocks included) by `$lib` or relative path;
- Vite `import.meta.glob` edges: `*` within a segment and `**` as a whole segment; braces, classes, extglobs and base-moving options fail closed.

It refuses each of the following with the import chain:

- filesystem, SQLite, network, process and `bun:` capabilities, and computed imports or globals;
- the local implementations, and any module of `src/routes/` (the folder browser among them);
- the memory doubles, and the gate doubles outside `hosted-gate`;
- any package outside its allowlist (`svelte`, `@sveltejs/kit`, `typebox`; plus the Kit modules `$app/env|forms|navigation|paths|state` and `cloudflare:workers`).

The allowlisted packages are not walked. `scripts/ci/hosted-artifact.ts` checks what was actually emitted for them: no import of a local-only module, no memory double, and gate doubles only in a gate artifact.

`bun run --bun probe:hosted-imports` commits one mutant per case in a disposable checkout under `.local/hosted/`, with its own generated Kit 3 tsconfig. It requires the real `check` to refuse each for its reason; `test:hosted` runs it.

`bun run --bun test tests/hosted-foundation/runtime` runs the contract diagnostics (memory doubles, both clients), the guard and the artifact scan. It claims nothing about Clerk, D1, R2 or workerd. Keep `bun run --bun test tests/e2e` distinct from the browser runner `test:e2e`.

### Hosted checks (GRS-138)

`bun run --bun gate:hosted` (`scripts/gate-hosted.mjs`) proves one exact revision of the hosted artifact, credential-free, the way `gate` proves the local app. It is the required check for a ticket that touches hosted paths. Before any step runs it refuses each of these, with `GATE FAIL <reason> <sha>`:

- `usage`: any argument (only `--stop` is accepted);
- `env`: a reduced-run variable of `gate`'s list, even empty;
- `dirty`: an uncommitted, staged or untracked file;
- `bindings`: `deploy/client/wrangler.toml` without the `DB`, `BUCKET` or `ASSETS` binding, a binding that is not `remote = false`, or an `account_id`;
- `preflight`: a missing tool. These are the skill's checks: Bun 1.4.2, the installed packages, a real Node >= 22, `unshare -rn`, `ip`, `mount` and Chromium.

Then it runs these steps, stopping at the first failure:

| Step | What passes it |
| --- | --- |
| `refusals` | `tests/hosted-foundation/gate/refusals.mjs`: a throwaway test for each refusal. Dirty tree, reduced-run variable and missing binding run the real gate in a throwaway clone of HEAD. Stale stamp and summary-not-evidence drive `runHostedGate` with its real validators on written evidence, one field changed per case. `failure-tail` checks that a failed run prints the cause from the step's log and at most 30 lines. `evidence-walk` (`mutations.mjs`, runnable alone) deletes, nulls, retypes, empties, flips, zeroes or adds a key to every field of each evidence file, the summary and `refusals.json`, about 4,000 mutants, and every one must be refused; only a step's own `evidence` record, an `ms`, drive's `startedAt` and one assertion fewer in a leg are free-form. An unchanged control must pass. It runs alone too, and isn't a Vitest file, because Vitest's globs do not collect `tests/hosted-foundation/gate/` |
| `net-offline` … `stop` | the [verify-clearcase-hosted](../.agents/skills/verify-clearcase-hosted/SKILL.md) lifecycle in one offline network namespace on port 43800, with the gate's checks inside it, in this order: `build` (`build:hosted`, hosted-gate profile, stamped with HEAD in full); `artifact` (`scripts/ci/hosted-artifact.ts`); `probe-check` (GRS-106's `test:check`); `start` (`start:hosted`); `live-doctor` and `live-doctor-negative`; `test:hosted` (the smoke legs and the import-boundary negative test with its mutants: 23 on 19 October, 21 refused and 2 controls, and the leg asserts only that there is at least one); `drive` (the feature map in Chromium, through the admitted browser lock; preflight refuses a run without admission); `stop` (`start:hosted --stop`) |
| `offline`, `cleanup`, `evidence-kept` | the namespace finished with every step PASS; the run's processes, scratch and server state are gone; the evidence is still there |

After the run the gate rereads every file the run wrote and judges it itself, so a step that exited 0 without evidence for HEAD fails. The files are the build stamp and `_app/version.json`, `health.json`, the `test:hosted` summary, `drive.json` and `inner.json`; a prefix of the SHA is not the SHA. Each is judged against one expected shape (`lib/evidence.mjs`: exact key sets, types and values, so a missing or unknown field fails) and the files are tied to one another: one build stamp and artifact digest across the build, health, test and inner files, one server state and fixture. It then checks that HEAD and the tree did not change, and writes `summary.json` (`clearcase-hosted-gate/1`). The summary names the exact SHA, the fixture (its sha256, the identity `client-a/a-viewer`, the wrong-client identity `client-b/b-editor`, the deployment's client), the tools and each boundary. It says `evidence: true` only when nothing was reduced, skipped, stale or failed. The gate validates that file again against an exact shape before `GATE PASS <sha>`: the boundaries equal the gate's own table and `notEvidenceFor` is exactly its list.

| Boundary | In a gate run |
| --- | --- |
| identity, store, assets, audit | `double` (the hosted-gate test doubles) |
| user work, results | `unavailable` |
| D1, R2 | `real-local`: Miniflare under `wrangler dev --local`, not Cloudflare's |
| runtime, browser | `real`: native workerd with Wrangler on Node; Chromium on the loopback origin only |

No gate run is evidence for Clerk, Cloudflare D1 or R2, email or a deployment; the summary's `notEvidenceFor` says so. Those stay with the proof tickets and the release gate.

Output: at most 30 lines, with one line per step and its seconds, and the drive's line naming each feature step and the browser-slot wait. A failure adds a `cause:` line from the step's log (the first GATE FAIL, forbidden or problem line) before the end of its error. Evidence and logs go to `.local/gate-hosted/<sha12>/<run>/`, or `$CLEARCASE_HOSTED_REPORT_DIR/<run>`. Scratch goes under `$CLEARCASE_HOSTED_SCRATCH/gate`, or `.local/gate-hosted/scratch`. One hosted gate per worktree (`.local/gate-hosted/pid`, the same flock admission as `gate`). `bun run --bun gate:hosted --stop` stops that group and cleans its stranded runs. A run took 2 min 33 s on the archlinux host on 19 October 2026: refusals 2 s, build 3 s, start 9 s, test:hosted 44 s, and a drive of 92 s, most of it waiting for a browser slot.

CI runs it as the third receipt step (`gate-hosted`) after `check` and `test`, with Node 24.22.0 (24 LTS) from `actions/setup-node`, `CI=1`, Wrangler telemetry off, `.local/hosted` and the scratch on the step's `/dev/shm` directory, and no Cloudflare account, binding or token. Its evidence uploads with the receipts. If the Node step fails (PC1 run 39260890102: Node 26.10.0 unpacked into the tool cache and its binary exited 127), the `node diagnostics` step prints the guest's kernel, mounts, loader and libraries, and `node fallback` puts nodejs.org's tarball of the same version first on `PATH` after checking its SHA-256 against a pinned value and the published `SHASUMS256.txt`. The gate step proves the `node` it runs is not Bun, and the receipt names its path. A hung namespace stops after 25 minutes, inside the job's 30, so a `gate-hosted` receipt is always written.

To prove one hosted user path in seconds without the gate's checks, run `.agents/skills/verify-clearcase-hosted/bin/verify-clearcase-hosted run`. Owners who replace a double (GRS-113, GRS-115, GRS-120) extend its feature map and change the gate's boundary entry in the same change.

Both listeners bind 127.0.0.1 only. A case folder that equals, contains or lies inside the data directory is refused; nothing is ever written into a case folder. The click import stores a case in `~/ClearCase` unless the operator picks another folder, which may not lie inside the data directory, the folder the server was started from (normally the checkout) or the chosen case folder.

### Analysis additions flag (GRS-48)

ADR 0003 puts three additions to the analysis views behind `CLEARCASE_ANALYSIS_ADDITIONS`, off until the client approves them. Off (the default) is v5's behaviour; exactly `1` shows all three:

- the defence matrix's free-text `Refs` column (`refsShown` in `src/lib/views/analysis/defence.ts`);
- `refs` as the defence CSV's last column (`defenceCsv(keys, rows, refs)`);
- headings equal to the navigation label on Timeline, Defence & Rebuttal and Info Required; off, they are v5's (`V5_HEADINGS` in `src/lib/views/analysis/headings.ts`). The navigation entry and the document title keep the label in both states.

Correctness fixes, such as timeline titles escaped once, apply in both states. `analysisAdditionsEnabled()` (`src/lib/analysis/data.server.ts`) reads the variable on each load, not through `config.server.ts`. `CLEARCASE_ANALYSIS_ADDITIONS=1 bun run --bun start` previews the additions; it records no client approval. The gate runs with the flag off: parity, the pilot suites and `verify:pilot:v5` start the app without it, and the parity register records the flag-off state. The analysis browser suite (`tests/e2e/analysis/suite.mjs`) passes its own environment's value to its app, so running it with `CLEARCASE_ANALYSIS_ADDITIONS=1` checks the flag-on state.

## Architecture

Start server work at `src/lib/local-case/app.server.ts`. For generic register work, start at `src/lib/views/registers/page.server.ts` and `src/lib/user-work/registers.server.ts`. Backup work starts at `src/lib/user-work/backup/backup.server.ts`.

- `src/lib/case-package/` is GRS-10's library (read-only here). GRS-70 extends it with the coordinator's sign-off: `zip.ts` `extractEntries` streams a case pack's entries to disk, and `v5/adapter.ts` reports conversion progress (`onProgress`). The demo build adds two more workspace generations to the v5 adapter, `v5/json-workspace.ts` and `v5/newer-workspace.ts` ([results-package.md](results-package.md#the-v5-adapter)). The app calls `importCandidate`, `verifyCandidateBytes`, `readCandidate`, `canActivate`, `acceptedWarnings`, `servePolicy` and `renderNarrative`; it never reimplements the contract.
- `src/lib/local-case/` is the app's server side (`*.server.ts`) and its browser-safe models:

  - `store.server.ts`: versions keyed by `resultsVersion`; `package_file` holds exactly `candidate.snapshot()`; verification is `verifyCandidateBytes` plus a digest over every projected row.
  - `project.server.ts`: the tested projector from `readCandidate` into read-model rows. Raw chronology rows are stored as canonical JSON, unchanged; display fields are derived, never written back; nothing is synthesised.
  - `service.server.ts`: import, activation, rollback, recovery, backups (below).
  - `case-pack.server.ts`: the click import (GRS-70). `listFolder` is the folder browser behind `/api/browse` (subfolders and `.zip` files with their sizes, never contents), and `prepareCasePack` extracts a pack, finds its workspace HTML and converts it into a results package in the storage folder before the import above validates it. A failed or cancelled run removes the folders it created.
  - `config.server.ts`: the settings in the table above, read once from the environment.
  - `originals.server.ts` and `viewer/`: the originals site and the pdf.js viewer.
  - `user-work.server.ts`: notes, seed overlays and register rows in `work.sqlite`.
  - `registers.server.ts`: the register store (GRS-52). Actions outside the generic register pages use `registers(userWork)` for register rows and seed deletions: a queue per case and store, insertion order, row versions (`stale`/`gone`), and `exclusive(caseId, fn)`, which a restore takes. A writer of a case's user work that does not go through the store (a defined table, rescan, notes) runs its write in `inTurn(userWork, caseId, key, fn)`, so a restore holds it back.
  - `answer.server.ts`: shared form-write failure helpers (`guarded`, `answer`) and `actionCase`, the case of the version an action posts to. Generic register pages map failures in their own `page.server.ts`.
  - `results.server.ts`: typed dataset access for views.
- `src/lib/components/`: the generated view registry and the shared view contracts.
- `src/routes/`: `/` (redirects to `/cases`), `/cases` (every case with its status), `/import` (the click import and the results-package form), `/import/[id]` (validation report and activation), `/recovery`, `/v/[vid]/overview`, `/v/[vid]/chronology`, `/v/[vid]/doc/[ref]`, `/v/[vid]/search`, each owner's views under `/v/[vid]/<category>/<view-id>`, the extension point `/v/[vid]/[category]/[view]`, and `/api/{health,state,browse,import-progress,v/[vid]/chronology}`. `[vid]` is the URL-encoded `resultsVersion`.

- `tests/e2e/pilot/run.mjs` runs the UI class suite and declares the reduced-run flags `CLASSES_ONLY` and `CLASSES_TARGET`.
  Both flags block gate admission. Class targets and exceptions live in `tests/e2e/classes/targets.mjs` and `declared.mjs`.

**Import.** Inputs are checked on every import. A rejection stores one attempt row with its diagnostics and nothing else; the active version is unchanged. A candidate is stored in one transaction and the results WAL is checkpointed. The same package again is a no-op while its fresh validation reproduces the stored diagnostics and read model. If the originals changed since it was stored (one went missing, say), the re-import is rejected with `APP_ORIGINALS_CHANGED` and the current diagnostics (for example `ORIG_MISSING`): a stored version never changes, so the operator either restores the originals byte for byte and activates the stored import again, or converts the case folder and imports a new results version. The activation refusal gives the same guidance. The same `resultsVersion` with another manifest, another case folder or a retired id is rejected.

**Activation.** Activating the current version is a no-op. Activating a different version revalidates before committing the pointer. In order: the stored bytes (`verifyCandidateBytes`); revalidation by `importCandidate({files: stored}, caseFolder, {trustedBaseline})`, which re-hashes the originals read-only; the fresh projection must equal the stored read model; `canActivate` on that fresh result with the operator's acknowledgement and the case's trusted baseline; then the pointer swap and the bound acknowledgement in `work.sqlite`, and a `VACUUM INTO` backup. The trusted baseline is the active version's accepted warnings plus an operator-accepted register, both scoped by case id. A refusal before commit changes nothing. A failed backup leaves activation saved and adds a warning. A committed change does not guarantee a successful backup.

**Startup.** Storage checks remove the app's leftovers, run `quick_check`, verify every active pointer against the activation log and fall back to the newest verified activation with a banner. Storage integrity failures become a 503 page with restore instructions. Invalid clock configuration, an occupied originals port or a refused instance lock terminate startup.

**An original removed or changed after import.** The document page checks its original when it renders, with the same cheap test the originals site makes before hashing (`OriginalsServer.availability`: the case folder recorded at import, the file opens inside it as a single-link regular file, the size is unchanged). If that fails, the page shows "Original missing on disk" with the reason and no Open or Download link, and the originals site answers 410; a same-size content change is still caught by the serve-time hash (410). Nothing is written and the version stays active. The operator recovers in one of two ways: restore the file at the path the page shows, byte for byte as imported (the links return on the next page load; the originals site re-hashes it against the imported sha256), or, if the case folder really changed, run the converter again, import the new results package and activate it (a still-missing original is then reported as `ORIG_MISSING` and acknowledged at activation). A container's page whose original is unavailable says so on each embedded attachment row ("the parent original is unavailable"), since those attachments are reached only through it. The overview's Originals counts are the check made at import, labelled with the import time; they are not re-checked live (the document page is). A file that was already missing at import cannot be restored into that version: the version records it as missing, and only a new results package (converter, import, activation) brings it in.

**Security.** The app origin sends a nonce CSP, `Referrer-Policy: same-origin`, COOP, CORP and `no-store`, checks the exact Host (the production listener also covers static assets) and relies on SvelteKit's Origin check for forms, which works without JavaScript. Imported values reach the DOM only as text, except GRS-10's `renderNarrative` output in `Narrative.svelte`. Originals are served only from the separate site, only through the verified mapping, only as verified bytes (else 410), with `servePolicy` headers; PDFs render only in pdf.js inside `<iframe sandbox="allow-scripts">` with scripting disabled. Cross-site navigations require a valid link capability. Cross-site framed requests are refused even with that capability. Requests with `Sec-Fetch-Site` set to `same-origin` or `none`, or with that header absent, bypass this capability check.

## Adding a view

The 42 navigation entries are generated from the coordinator's inventory (`docs/plan/view-coverage.json`) into `src/lib/components/view-registry.ts` by `scripts/pilot/generate-view-registry.ts`; `check` fails on drift. Each entry has an id, label (the task name that is also the destination's heading, BA-18), group, owning planning key and Linear issue, route category, route and status.

A view owned by an M2 ticket lives at `/v/[vid]/<category>/<view-id>/`, where the category is the owner's: `evidence` (CC-04, GRS-14), `analysis` (CC-05, GRS-15), `quantum` (CC-06, GRS-16), `registers` (CC-07, GRS-17), `litigation` (CC-08, GRS-18), `bundles` (CC-09, GRS-19), `system` (CC-10, GRS-20). Until the owner's route exists, `src/routes/v/[vid]/[category]/[view]/` renders the entry's explicit "not yet available — owned by GRS-nn" state.

To build one:

1. Create `src/routes/v/[vid]/<category>/<view-id>/+page.svelte` (and `+page.server.ts`). SvelteKit prefers this static route to the extension point, so nothing else changes.
2. Wrap the page in `<main id="main" tabindex="-1">` and start it with `PageHeader` (`heading` = the registry label, `section` = the label, `caseName` from the layout data); put export controls in its `actions` snippet.
3. Read results with `datasetOf(app().store, version.id, '<dataset key>')` from `$lib/local-case/results.server`; the `/v/[vid]` layout has already verified the version. Use `readCandidate`-equivalent semantics: recognized datasets only, values untrusted.
4. Read the current time only through `now()` from `$lib/components/clock` (a `Date`), never `new Date()` or `Date.now()`, for anything shown or stamped: deadline countdowns, "today", ages. It is the real clock unless `CLEARCASE_FIXED_NOW` is set (for example `CLEARCASE_FIXED_NOW=2030-01-31T09:00:00Z`), which tests and the verification skill use to make date-sensitive views deterministic; an invalid value throws rather than falling back. The server checks it first at boot: an invalid value is a configuration error that exits with one `FATAL: CLEARCASE_FIXED_NOW must be …` line and code 1 before the data directory is opened, like a taken originals port (the startup checks themselves never throw). The root layout passes the setting to the browser, so `now()` agrees on both sides. Timers, timeouts and lock stamps keep the real clock.
5. Put every imported value into text nodes. Render authored narrative only with `Narrative.svelte`. Resolve citation refs with `resolveRefs` from `$lib/local-case/documents.server`, which includes provider rows. `store.existingRefs` sees imported rows only. Link documents with `CitationLink.svelte` or `docPath`; open originals with `OriginalOpen.svelte` and links built on the server by `originals()`.
6. Read document rows through the document-row contract, never from the chronology dataset directly (see below).
7. Keep user work in `app().userWork`: registers (store name `^[a-z][a-z0-9-]{0,63}$`, flat fields of text, finite numbers, booleans or null, at most 64 KiB), `putSeedOverlay`/`seedViews` for seeded registers, `addNote`/`notesFor` for notes. The register API:
   - **Use the core register store outside generic register pages.** Open `registers(app().userWork).open(caseId, store)` from `$lib/local-case/registers.server`. `rows()` lists the rows in insertion order (it keeps the integer `seq`, so you do not), each with a `version`; `add(fields, {addId})` stores a row after the last. The same `addId` and fields suppress a duplicate only while the current process retains the entry in its 500-entry cache. This is not durable idempotency. `replace(rowId, version, fields)` and `remove(rowId, version)` act on the row as the page showed it and answer `'stale'` when it changed since or `'gone'` when it is gone (never re-created); `batch(tx => …)` runs several writes as one step of the queue. Send the row's `version` to the page in a hidden field and back with the write (`null` skips the check). `registers(userWork).seeds(caseId, resultsVersion, datasetKey)` lists seeded rows and `remove`s an imported one by overlay. The store queues the writes per case and store, so two presses cannot compute the same `seq`, and `exclusive(caseId, fn)` holds back a case's writes for a restore (writes made inside `fn` run inside it).
   - **Answer a failed core-store write with `guarded`/`answer`** from `$lib/local-case/answer.server`: `guarded(op, values, () => write, say)` returns `{ok, value}` or `{ok: false, failure}`, and the `failure` is a `fail(status, {op, values, message, retry})` that keeps the user's typed values (503 busy offers a retry, a refused write 400, any other fault 500, logged and never shown). Give it your `Say` (the three sentences for busy, refused and failed). In an action, `actionCase(params)` gives `{vid, caseId}` of the version posted to (an unknown version is a 404). Use these helpers for core register-store actions. Generic register actions use `src/lib/views/registers/page.server.ts` and `src/lib/user-work/registers.server.ts`. They share `inTurn` with the core store but keep their own sequence, row-version and failure logic.
   - Underneath, `putRow(caseId, store, rowId | null, fields, anchor?)` inserts (`rowId` null; returns the new UUID) or replaces a row, `listRows(caseId, store)` returns `{rowId, store, anchor, fields, createdAt, updatedAt, intact}` ordered by `createdAt`, then `rowId` (**not** insertion order: rows written in the same millisecond tie, and under `CLEARCASE_FIXED_NOW` every row has the same `createdAt`), and `deleteRow(caseId, store, rowId)` answers whether a row was deleted. The store calls these; a view calls them only for a read that needs no order.

   A view that needs its own table defines it with `defineTable` (see "Defining a table" below; `scope` is required). Call it once per process, before first use, for example lazily in your module's first loader or action, guarded by a module-level promise (`defined ??= app().userWork.defineTable(def)`, then `await defined`). Redefining is idempotent but runs a write transaction. Then read and write the table only through:
   - `putTableRow(table, row, {owner})`: inserts or replaces the **whole** row with that primary key; a missing cell is NULL. To change one field, read the row with `listTableRows`, spread it and put it back (`{...row, title}`). Cells are checked as in a restore, and a case table's row needs a text `case_id`. Declared types are enforced for `INTEGER` keys (an integer) and `TEXT` cells (a number in a `TEXT` column is `invalid`, since SQLite would store `7` as `'7.0'`: pass text); other non-key cells are not coerced. It is refused for a table that `owner` does not own (`table-conflict`), a built-in table (`table-built-in`), and a table not defined through `defineTable` (`invalid`).
   - `deleteTableRow(table, key, {owner})`: deletes by primary key; in a case table the key also names `case_id` as text (without it the call is `invalid`), so another case's row is never deleted. A number in a `TEXT` key is `invalid`. Returns whether a row was deleted.
   - `listTableRows(table, {caseId?})`: rows in primary-key order, with cells as `exportAll` writes them. `caseId` is required for a case table and refused for a store table.

   Table-row mutations schedule the `work.sqlite` backup after commit, as `putRow` does. `defineTable` commits schema and catalogue changes without scheduling a backup. A raw `app().storage` write schedules no backup. Never key user work by array index, display position or ref alone.
8. Add tests next to your code and a feature file in the verification skill (`features/`), and drive the view in your browser tests.
9. When your ticket passes its gate, the coordinator adds its planning key to `PASSED` in `scripts/pilot/generate-view-registry.ts` and regenerates the registry, which marks every view of that owner available.

Register money, rate and hours parsing lives in `src/lib/views/registers/amounts.ts`: `parseAmount` distinguishes empty, invalid and valid input, with valid amounts represented as `bigint` hundredths. Decimal commas, exponents and more than two decimal places are refused with a reason.

### Document-row read contract

`documentRows(store, resultsVersion)` and `activeDocumentRows(app(), caseId)` in `$lib/local-case/documents.server` return every document row of a version: the imported register in source order, then rows from registered providers (the equivalent of v5's `allRows()`). Each `DocumentRow` is frozen and carries `ref`, `ord`, `source` (`'results'` or `'provider:<id>'`), the raw source `row` unchanged, its list projection `list` (`ChronologyListRow`) and its `state` (`DocumentStateRow`). `listJson` is the chronology list and its ETag as served by `/api/v/[vid]/chronology`; `documentRow(store, rv, ref)` is one row by ref (the document page reads it, so provider rows have pages); `documentCounts(store, rv)` is the row count the overview shows. GRS-20's rescan publishes rescanned rows with `registerDocumentRowProvider({id: 'rescan', owner: 'GRS-20', rows, revision})`; readers do not change. A provider row whose ref already names an imported document (or one the provider already gave), or whose `list.ref` is not its own `ref`, is dropped and reported in `dropped`, never shadowing or duplicating the register. `revision()` must return a safe ETag token: 1 to 128 characters of `A-Z a-z 0-9 . _ : + / = -` (`REVISION`). A provider whose `revision()` or `rows()` throws, returns the wrong type or an unsafe revision, or whose row list cannot be read, is isolated: its rows are left out, it is reported in `failed`, the chronology API still answers 200 (with an `x-clearcase-degraded` header and a distinct ETag), and the chronology and overview say "Some documents are not shown" (`DegradedRows.svelte`). The chronology page's universal load reads that header, so `hooks.server.ts` lets exactly that header through SvelteKit's SSR serialization (`filterSerializedResponseHeaders`); the list body stays the stored bytes. A malformed provider row (not an object, no non-empty, well-formed Unicode string `ref` (`isWellFormed()`: a lone surrogate would break the page's links), `row` not an object, `list` or `state` failing the checks below, not JSON data, or a property read that throws) is dropped and reported in `dropped` (`ref` is `#<index>` when it cannot be read) and the other rows are shown. Each row is copied as JSON first, reading every property once, and the copy is what is validated and shown, so readers see the checked JSON copy. Validation is partial: `state.preview` accepts any string, `flags` only needs to be an array, and `self` only needs to be an object or null. A thrown value that cannot be turned into text is reported as such; it never escapes provider isolation. A `state.original` without a non-empty `path`, a non-negative integer `size`, a lower-case hex `sha256` and a string `mediaType` is replaced by `null` (the page shows no original) and reported in `dropped`; the row is kept. `dropped[].reason` is a `DropReason`. Thrown provider and getter messages are preserved up to 200 characters, so failure reasons can include row values.

### Enumerable user-work persistence

Every `work.sqlite` table is enumerable: `app().userWork.tables()` introspects SQLite and labels each table from `work.userwork_catalog` as `user-work`, `activation` or `unregistered` (a table created outside the API is still listed), with its `scope`. `exportAll({kinds?})` returns a `clearcase.user-work/1` snapshot of every row, each table with its metadata (`name`, `kind`, `scope`, `owner`, `description`, `columns`). BLOBs are `{"$b64": …}`; INTEGERs are read as BigInt, and one beyond the JavaScript safe range is written as `{"$int": "<decimal>"}`, so no value is rounded and no value fails the export. `importAll(snapshot)` restores it in one transaction, creating any table the snapshot defines inside that same transaction (an unregistered table stays unregistered), so a refused or failed restore leaves no table behind. A table that already exists must have the snapshot's schema (ordered column names, declared types compared case-insensitively, NOT NULL, where a key column always counts as NOT NULL, and the ordered primary key) and scope; any difference refuses the whole restore before a row is deleted or written, naming the table and the difference, so no value is coerced into another type. Migrate such a table first. Only SQLite's own `sqlite_*` tables and the catalogue (`userwork_catalog*`) are hidden from `tables()`. `registerStores(caseId)` lists the register stores in `register_row`.

**Invariant.** A snapshot from `exportAll()` always restores with the default mode, into the same store (also after later edits, except where a later edit gave another case a snapshot row's key: see `restore-key-collision`) and into a fresh store. `exportAll` and `importAll` decide whether a table restores with one function, `restorePlan` in `user-work.server.ts`, and `exportAll` applies it to each table twice: against this store and against a fresh store. A table either check refuses is not exported but listed in `excluded` with its row count and the reason (prefixed `in a fresh store:` when only a fresh store refuses it): no primary key, a column type other than the four (for example `NUMERIC`), a name outside the rules, activation or import state, an empty or non-integer key (for example `1.5` in an `INTEGER` key), a repeated key, a non-finite number, NULL in a NOT NULL column, a non-text `case_id` in a case table, a key or `case_id` column with a non-`BINARY` collation (for example an unregistered table with `id TEXT COLLATE NOCASE PRIMARY KEY`), or a store table with a `case_id TEXT NOT NULL` column that a fresh store's restore would make a case table. Excluding a non-`BINARY` table keeps its rows only in the store's own file backups: a restore could not merge it safely, because it would match keys that differ in letter case or trailing spaces. The collation is read with a probe index inside a savepoint that is always rolled back, so `exportAll` briefly takes the `work.sqlite` write lock but never changes the store. A collation on a non-key column is exported and restored.

**Defining a table.** A ticket that needs its own table calls `defineTable({name, owner, description, columns, primaryKey, scope})`: lower-case names not starting with `sqlite` or `userwork_catalog`, `TEXT`/`INTEGER`/`REAL`/`BLOB`, unique column names and a primary key of stable ids with no column listed twice, and text `owner` and `description`. It is idempotent, and GRS-20's backup round-trips the table with no per-table code. Redefining an existing table (matched in any letter case, as SQLite does) needs the same schema, including the ordered primary key, the same owner and the same scope; a table that exists under another letter case is refused. Adopting a table created outside the API is also refused when a key column or `case_id` has a collation other than `BINARY` (for example `NOCASE`), since a restore matches keys and cases byte for byte; a restore into such an existing table is refused the same way. Redefining a table already catalogued with the same owner and scope reads only its primary-key index, without the probe index an adoption builds, since a table the API created is `BINARY`. The built-in tables (`note`, `seed_overlay`, `register_row`, `trusted_warning`, `active`, `activation_log`) and the `results.sqlite` table names cannot be defined.

**Scope** is required and declared, never inferred from a column name. A definition without `scope` is `invalid`:

- `scope: 'case'`: every row belongs to the case in its `case_id` column, which must be `TEXT` and NOT NULL (`notNull: true`, or part of the primary key). All built-in tables are case tables. Registers and other per-case work (CC-07 "scope records to the selected case") use this.
- `scope: 'store'`: rows shared by the whole store. A store table must not have a `case_id` column, so an owner who wants per-case rows has to say `'case'`. A per-case column under another name (`case_key`, `caseId`) makes nothing per-case: the table is a store table and a restore merges it.
- Why required: a store table is merged by key, whichever case wrote a row. If a per-case table without `case_id` silently became a store table, and its keys repeat across cases (for example reused integer ids), restoring one case's backup would overwrite another case's rows with the same keys. A required scope makes the owner choose. Keep `case_id` in a case table and its key; give store-table rows keys that are unique across the whole store and never reused.
- The scope never changes once a table exists. `defineTable` with `'case'` on a table recorded or treated as `'store'` (including a table created outside the API, or catalogued before scopes were recorded), or the reverse, is `table-conflict`.
- The scope is recorded in the catalogue (the companion table `work.userwork_catalog_scope`, created on first use; `db.server.ts` seeds `userwork_catalog` without a column list, so that table gains no column). A table without a recorded scope (unregistered, or defined before scopes existed) is a store table. A snapshot table without a `scope` field (written before scopes existed) keeps the scope of the table it restores into. When the restore creates it, it is a case table if it is catalogued and has a `case_id TEXT NOT NULL` column, otherwise a store table. A restore refuses to create a catalogued table with such a column as `'store'` (`invalid`), as `defineTable` does, so it never creates a table its owner's `defineTable(scope: 'case')` cannot adopt.

**Restore rules** (`importAll(snapshot, {replace?, cases?, clearAbsent?})`, default `'cases'`):

- By default, the restore cases are the `case_id` values of the snapshot's case-table rows, outside `trusted_warning`. Explicit `cases` replaces this inferred list.
- A case table: existing rows for the restore cases are deleted, then the snapshot's rows are inserted. Other cases' rows are kept. Before any write, no snapshot row may have the primary key of a row of **another** case here (possible only when the key does not include `case_id`, as for `note.id`). Keep `case_id` in a case table's key, or use ids unique across cases. Without explicit `cases`, a snapshot with no case rows leaves case tables unchanged.
- A store table is merged by primary key: snapshot rows replace same-key rows, and other rows are kept. It is never replaced wholesale in this mode. So a merge brings back rows deleted since the backup and overwrites later edits of the same keys, while rows added since are kept.
- `{replace: 'tables'}` replaces every snapshot table as a whole, deleting other cases' and other keys' rows too. Use it only for a full restore of one store into another.
- `trusted_warning` is never written: a restore never creates trust. Its rows are dropped and the store's own accepted warnings are kept, so the operator acknowledges those warnings again.
- With `clearAbsent`, `replace: 'cases'` and a non-empty case list, explicit or inferred from the snapshot, restore reports can also contain `cleared-for-cases` and `kept-excluded`, in addition to the five actions below.
- `ImportResult` is `{tables, rows, cases, restored, dropped?}`. `cases` lists the cases selected for restore. Without `clearAbsent`, `restored` has one `{name, scope, action, rows, deleted}` per snapshot table, in snapshot order, so a backup UI can show what happened. For a table in the snapshot, `action` is one of:
  - `replaced-for-cases`;
  - `no-cases`: a case table left unchanged because the snapshot holds no case rows;
  - `merged`;
  - `replaced` (`'tables'` mode);
  - `dropped` (`trusted_warning`).

  `rows` counts the snapshot rows written and `deleted` the rows removed first. A `merged` entry also has `inserted` (rows whose key was new here) and `replaced` (rows whose key was already here and now holds the snapshot's row), which add up to `rows`. A `replaced-for-cases` entry also has `cases`, the snapshot's cases this table had rows of here or gets rows of (sorted), so a backup UI can name the cases affected. `rows` and `deleted` are counts per table, across all of those cases, not per case. The fields are additive; a reader that ignores them sees the round 2 shape. `dropped` (`{name, rows, reason}`) is present only when trust rows were dropped.

**Validation and refusal errors** use `UserWorkError` with a `code`. Its message names tables and columns, never row values. Transaction contention or unavailable store files can throw SvelteKit `HttpError(503)`, which the action must handle. Everything is checked before the first write except a constraint that only SQLite can see, such as another UNIQUE index on an unregistered table; that rolls back as `invalid`. The codes:

- `invalid`: bad input. This covers a missing or unknown `scope` in `defineTable`, a table-row call on a table not defined through `defineTable`, a number in a `TEXT` column of a `putTableRow` row or `deleteTableRow` key, a `deleteTableRow` key of a case table without a text `case_id`, a restore creating a catalogued table with a `case_id TEXT NOT NULL` column as `'store'`, a missing `caseId` (case table) or a given one (store table) in `listTableRows`, a row with a column the table lacks, a snapshot or table entry that is not an object (including a `null` entry), a table listed twice, a name taken by an index, view or trigger here, another schema or scope, and a cell that is not a string, a finite number, null, `{$b64: <base64>}` or `{$int: <decimal in the signed 64-bit range>}` (booleans, arrays and other objects are refused). It also covers NULL in a NOT NULL column, a non-text `case_id` in a case table, bad `defineTable` input, or a write that failed for another reason, with nothing written. A `putTableRow` row or restore row is also checked as SQLite stored it, after column affinity (`INSERT … RETURNING`): numeric text that a `REAL` or `INTEGER` column turns into an infinite number (`'1e999'`, `'-1e999'`, a 400-digit integer) is `invalid` and rolls the whole write or restore back, so a refused value never removes valid rows from a later export. Text that SQLite keeps as text (`'NaN'`, `'Infinity'`), or turns into a finite number (`'99999999999999999999'` in an `INTEGER` column becomes the `REAL` `1e20`), is stored and exported as SQLite holds it.
- `restore-state`: the snapshot carries an activation table (`active`, `activation_log`, or any table of kind `activation`) or a `results.sqlite` (import state) table name. Activation is never restored; `exportAll({kinds: ['activation']})` lists those tables in `excluded`.
- `restore-key`: a primary-key cell of a restore or `putTableRow`/`deleteTableRow` row is empty (NULL or missing), not an integer in an `INTEGER` key column (including an `$int` outside 64 bits), or the same key appears twice in one table. "The same" is as SQLite stores it in the column: in a `TEXT` key, `7` and `'7.0'` (or `{$int: '1'}` and `'1'`) are one key; in a `REAL` key, `1.5` and `'1.5'` are one key. Such a snapshot is refused before writing, in every mode. A restore otherwise accepts a number in a `TEXT` column (`exportAll` never writes one).
- `restore-key-collision`: a snapshot row of a case table (in case scope) or a `putTableRow` row has a key held by a row of another case here.
- `table-conflict`: `defineTable` on an existing table of another schema, owner or scope, one in another letter case, or one with a non-`BINARY` collation on a key or `case_id` column; a restore into an existing table with such a collation; a table-row write by an owner other than the table's.
- `table-built-in`: `defineTable` or a table-row call on a built-in or `results.sqlite` table.

### Overview widget slots

The overview has typed widget slots declared in `src/lib/components/overview-slots.ts`: `deadlines` and `unbilled-time` (GRS-17, category `registers`) and `rescan-freshness` (GRS-20, category `system`). An owner fills its slots from its own subtree: `src/lib/views/<category>/overview-widgets.ts` exports `widgets: OverviewWidget[]` (`{slot, component}`, a Svelte component receiving `{data, ctx}`) and `src/lib/views/<category>/overview-widgets.server.ts` exports `loaders: OverviewWidgetLoader[]` (`{slot, load(ctx)}`, with `ctx.app` the server's `LocalCase`). Both are discovered with `import.meta.glob`; the category in the path must be the slot owner's, a slot may be filled once, and a loader that throws, does not settle within `SLOT_LOADER_TIMEOUT_MS` (5 seconds), or returns data the page cannot carry, marks only its slot ("This summary could not be loaded."); the other slots and the overview still render. The timeout bounds only waiting on a pending promise. It cannot interrupt a loader that computes synchronously (`node:sqlite` reads are synchronous): such a loader blocks the whole server until it returns. Keep loaders asynchronous where they wait, and bounded within the overview budget where they compute. Plain data is primitives, arrays, plain objects, `Date`, `Map` and `Set`: not a function, a class instance, a symbol or a thenable, no own `__proto__`, `constructor` or `prototype` key, and nested at most `MAX_SLOT_DATA_DEPTH` (100) levels deep. That is a subset of what SvelteKit's serializer (devalue) accepts. Until a slot is filled the overview shows "Not yet available — owned by GRS-nn". New slots are added to `OVERVIEW_SLOTS` by the coordinator.

**Paths a view owner may write:** `src/routes/v/[vid]/<category>/**` for their own category, and the owner-specific paths the coordinator reserves at dispatch: proposed `src/lib/views/<category>/**` (where overview widgets live), `tests/e2e/<category>/**`, and their own feature files under `.agents/skills/verify-clearcase/features/`.

**Coordinator-serialized files** (one writer at a time, through the coordinator): `package.json`, `bun.lock`, `tsconfig.json`, `vitest.config.ts`, `svelte.config.js`, `vite.config.ts`, `src/app.*`, `src/hooks.server.ts`, `static/**`, `src/routes/+layout.*`, `src/routes/+error.svelte`, `src/routes/v/[vid]/+layout.*`, `src/routes/v/[vid]/[category]/[view]/**`, `src/lib/components/**` (shared contracts and the registry), `src/lib/local-case/**` (storage, persistence API, originals), `scripts/pilot/**`, `tests/e2e/pilot/lib/**`, and the skill's `SKILL.md` and runner.

If moving source lines (for example in `src/lib/views/registers/logic.ts`) makes its `--check` report drift, regenerate with `bun scripts/verify/register-dispositions.mjs`; it locates literal evidence patterns and rewrites the recorded file:line references.

## Synthetic corpus

Run `bun run --bun fixtures:generate --out /tmp/clearcase-synthetic --seed demo --documents 1689 --profile small`.
The output must not exist; its parent must exist outside the checkout, including through symlinks.
Defaults are seed `20261017`, 1,689 documents and profile `small`; no case input is accepted.
Output contains `pkg/` (results package), `case/` (invented originals) and deterministic `generation.json` (sizes and SHA-256s).
The generator reuses the pilot fixture helper and real v5 converter, covering all 35 named dataset schemas.
`small` uses tiny valid PDFs/PNGs; `poc` targets 60% at 16–128 KiB, 30% at 128 KiB–2 MiB, 9% at 2–8 MiB and 1% at 8–32 MiB, plus format overhead.
Those bands are synthetic; repeating inert padding measures byte volume, with no claim about case distributions, compression, rendering, OCR, all 42 views or hosted boundaries.
Seeded dates occupy 2200–2209 (prescription through 2212), excluding 1900–2099 to avoid modern case-date leak needles.
Invented names hyphenate vocabulary pairs (`Synthetic Hazel-Moss`), because a space between a given name and a surname could spell a real person's name.
`bun run --bun test tests/fixtures` proves validation, activation policy, determinism and those date and name shapes only. AC2 is proved by `bun run --bun test tests/e2e/pilot/synthetic-corpus.test.ts` (also collected by the gate's `test` step).
It generates the default 1,689-document corpus with the default `small` profile, imports and activates it through real SvelteKit HTTP form actions (303 redirects), and asserts a 200 chronology API response with exactly 1,689 rows.
The test uses disposable scratch SQLite storage and removes it and the generated corpus afterwards; `poc` byte-volume performance is outside this acceptance proof.

## Known limits

- The store API is synchronous over `node:sqlite` (writes are async transactions). The V2 move to D1 needs an async seam; the judge recommended one from the start.
- A hard-linked original is accepted by GRS-10 at import but refused (410) when served, because a hard link may share bytes with a file outside the case folder.
- Original bytes are re-read and hashed on every request; there is no `(path, size, mtime) → sha256` cache yet.
- All 42 views are implemented and marked available in the view registry, and strict parity compares each with v5 (the CC-11 matrix). The [demo runbook](demo-runbook.md#importing-the-newer-ess-pack) records that the newer 2,131-document export imports and that every view opens. No parity run covers that export yet; that check belongs to CC-12.
