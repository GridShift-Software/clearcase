# Synthetic native operator workbench

Prepared UI and read helper, not processing or live acceptance evidence. Entry: `/operator/cases/[caseId]`.
Only synthetic submissions and already-processed synthetic results belong in this alpha.

## Operator steps

1. Sign in as staff with the case's explicit operate/download access. Open the workbench and refresh finalized submissions and candidates. A reserved upload is not a finalized submission.
2. Select the exact finalized submission. Inspect/download its persisted manifest and PDF through the existing audited download endpoints. This page never starts processing, claims a processing job, or asserts processing lineage.
3. Select the **root directory of an already-produced results package**, containing `manifest.json`, `assets.json`, and `datasets/*.json`. The browser preserves each file's UTF-8 text and constructs the existing import controller's exact JSON:
   ```json
   { "operationId": "<stable-operation-id>", "submissionRevisionId": "<selected-finalized-revision>", "files": { "manifest.json": "<exact UTF-8 text>", "assets.json": "<exact UTF-8 text>", "datasets/chronology.json": "<exact UTF-8 text>" } }
   ```
   See [the actual package contract](../results-package.md). JSON contents are not rewritten, normalized or processed. The UI supports at most 200 files and 24 MiB; the deployment's authoritative budget may be smaller. A BOM is preserved for the real validator to reject. ZIP, HTML case packs, PDFs, Markdown recipes, arbitrary extra files and malformed UTF-8 are not supported by this workbench's upload picker. ZIP support in the package library is **not** ZIP support in the native import controller.
4. Import privately. A refused or unlinked response is shown with its actual HTTP status/code/details; staging alone is not a linked candidate, sign-off or publication. Inspect the private candidate link/status. The advanced correction editor sends the existing `{operationId, reason, replacements:[{key,data}]}` DTO and cannot edit originals or generated datasets through the server's correction rules.
5. Select the candidate's finalized submission, refresh readiness, and review the exact identity and warning fingerprints. Any required section, preview or validation error holds sign-off. Supply a reason for each new warning, explicitly confirm self-approval when required, and type the exact reviewed resultsVersion. Click **Record exact sign-off**. This never publishes.
6. Refresh readiness with the returned sign-off id. Only the exact current, audited and non-invalidated sign-off enables publication. Explicitly select the expected pointer state (none/published/withdrawn, with its exact version when applicable), type the version to publish, and separately click **Publish**. The existing controller's atomic comparison/receipt rules remain authoritative. The page never infers the current pointer from a candidate, readiness response, sign-off, or pointer equality.

Before displaying a confirmed write, clearing its pending request, rotating any operation id or applying candidate/sign-off state, the browser validates the complete success DTO. Import checks the selected finalized submission and exact supplied manifest hash/version/input identity; correction checks its frozen parent, client/case/submission/input pins, reason and requested change paths; sign-off checks its operation-derived id, exact submitted version and self-approval; publication checks the exact operation id and reviewed target version. Linked response shapes, nested coverage/correction records and internally derived candidate/link ids are checked too. These checks use the identities the existing DTO actually returns: correction does not return package bytes, sign-off does not echo its full identity, and publication does not echo the signed identity. They are consistency/recovery checks, not independent content verification or boundary proof. A malformed or mismatched 2xx leaves the identical pending request and id intact and reports an unconfirmed outcome.

Draft reasons and correction text remain on refusals and stale reads. Writes disable inputs while in flight. Network/invalid-response/5xx failures retain the exact request in memory for an explicit unchanged retry, including its original operation id; the controller reconciles it. Do not reload during an uncertain operation: closing/reloading loses in-memory drafts/retry material. A confirmed controller response is displayed as such, not as proof of processing or a live deployment. No-JavaScript rendering explicitly refuses interaction. Imported text is escaped; there is no raw HTML rendering, package logging or client-side authorization.

## Readiness DTO and parent composition

`GET /operator/publication/[caseId]/readiness?candidateId=<id>[&signoffId=<exact-id>]` is private/no-store. `setReadinessComposition` in `src/lib/publication/hosted/readiness.ts` is its **own** per-request composition hook. It defaults to null/503. The parent must register a resolver against the **exact original Request** and supply that request's real `PublicationReadinessPorts`: the existing `NativePublicationPorts` plus `readinessFence: ReadinessFence` (`protocol: 'coherent-readiness/1'`). An absent/wrong-protocol fence stays 503 before metadata access. The existing publication composition setter does not configure this one.

The helper requires verified staff of this client, current explicit `publish` authority, and current case `read-preview` access before snapshot/ledger metadata. Mandatory `publication.readiness.intent` and `publication.readiness.release-intent` audits precede release; their success means intent recorded, **not completed disclosure**. The old premature `publication.readiness.read` success is removed, not reinterpreted. Fence refusals append `publication.readiness.refused` with refused/denied/failed outcome; audit failure releases nothing. No successful-release audit is claimed. The existing authority checks and separate sign-off/material rereads remain early refusal checks only. After **all** awaited audit, hash, authority and storage work, the final fence checks the original complete observation. On `current`, response serialization is synchronous with no later port call or await; on stale/forbidden/invalid-session/fault it releases only an error DTO (409/403/401/503).

It uses `checkSnapshot`, `signoffBlocker`, `newWarnings`, and the existing canonical SHA-256 helper. Snapshots or arrays beyond the helper's bounds fail unavailable rather than truncate acknowledgements. The response contains only `{caseId, identity, materialSha256, blocker, requiredAcknowledgements, selfApprovalRequired, signoff}`. Sign-off observations contain only its id, bound identity, audit state, invalidation flag and actual effectiveness/staleness blockers. Stable recorded/invalidated/stale sign-offs remain inspectable with their true blockers. No signer details, audit envelope, storage keys, original text, signed decision or applied-publication claim are returned.

The browser checks identity against the selected finalized submission and candidate, and rereads readiness before every **new** sign-off/publication request. Changed identity, warnings, material, or sign-off observations refuse submission and require deliberate review again. An unchanged retry of an uncertain operation intentionally goes to the existing controller's reconciliation path, not a new client decision. These checks are UX, never authority.

### Required parent hooks and linearization

- Import `d1ReadinessFence` directly from `src/lib/publication/hosted/readiness-fence.ts` and compose `readinessFence: d1ReadinessFence({db: env.DB, clientId})`. Pass the **raw same-client primary D1 binding**, not a replica session, separate DB, boolean or callback allow. It runs exactly one `withSession('first-primary')` SELECT per check. No shared controller/ledger/authorizer/audit module or migration is changed here.
- Install the existing [atomic-publication migration prerequisites](atomic-d1-publication.md#exact-composition-and-other-owner-hooks), including the durable candidate audit-settlement schema and `0002_atomic_publication.sql`. Supply the real generation-fenced candidate assembly and exact ledger, audit, authorizer and atomic publisher on that same DB. Snapshot generation must be read before and after assembly; missing/different generations refuse. Every required-section, preview, validation, original or other snapshot dependency must be immutable/version-addressed or advance `pub_candidate_generation` in its write transaction. Untracked mutable configuration/provider readiness cannot be composed as safe. There is still no assembled material adapter here.
- The SELECT simultaneously checks the observed generation, immutable link/version/preparer pins, stored/non-withdrawn results, durable native candidate audit settlement, no supersession, the exact current `rs_trusted_fingerprint` set (not covered by candidate generation), and the **whole requested sign-off**, including state/invalidation and warning acknowledgements. No requested sign-off means no sign-off claim, not a search for an inferred approval. No current-publication pointer is consulted.
- SQL independently requires current active/unexpired staff case `publisher` and `content` (`viewer` or `editor`) grants; operator/admin membership alone is insufficient. Positively observed local session revocations use existing `pub_session_revocation`, committed before acknowledging local revocation. Keep the real original-request `checkRevocation`, publish authorizer and preview authorizer: D1 grants are not authentication.
- The single SELECT is the coherent **D1 observation point** for material, ledger and local authority. External Clerk is last observed by the fourth `authority()` call (its `checkRevocation()` precedes publish/preview authorizer awaits), before the final ledger/candidate reads and SQL guard. Clerk can change after that observation; D1 cannot lock it. Likewise a legitimate D1 change after the SELECT can precede response delivery. This is point-in-time readiness, never eternal currentness or an approval/publication decision; the unchanged publication controller must still validate and serialize every write.

The parent also owns real import stager composition, original-request runtime registration, D1/Clerk setup, navigation and combined-SHA native browser proof. All mutations use direct same-origin JSON calls to existing endpoints, preserving Origin enforcement; there are no server actions or cloned-request composition lookups.

- `bun run --bun check:hosted-imports`.

`coherent-readiness.test.ts` executes the production SQL against the existing schemas on file-backed SQLite with two connections and a D1-shaped transport; it is **not native D1 evidence**. It covers ledger invalidation during the final candidate await, baseline/generation/preview/grant/session races, settlement, native eligibility, guard/fault/missing-port refusal, intent/refusal audit semantics and a legitimate change after the linearization point. Existing test names/assertions remain; their composition gains the fence and audit-action expectations use the truthful release-intent name. M2 component and retry tests are unchanged.

The adverse test changes warning-baseline material during an awaited audit without changing the displayed identity: readiness must refuse 409. The retained named probes also cover a warning-baseline edit during the fourth/final preview authorization, denial/release-audit failure, and an empty 201 import success. New function-level regressions cover malformed successes, missing nested DTO fields, mismatched submitted identities and byte-identical uncertain-operation retries across import, correction, sign-off and publication. These do not exercise hydration. Other checks cover absent hooks, original Request binding, grant/preview denial before metadata, audit outage, late session revocation, hard blockers, stale sign-offs, deliberate reasoned sign-off payloads, real-controller Origin refusal, and escaped server rendering. These are targeted unit/render checks, not acceptance-boundary evidence. Full suites, processing, provider calls, browser/workerd/full builds, real Clerk/D1/R2 and deployed publication/import boundaries are unrun here; the integration owner must prove them at its combined exact SHA.
