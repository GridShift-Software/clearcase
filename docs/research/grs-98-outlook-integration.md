# GRS-98: Outlook drafts and user-controlled case-email import

Research only, from public Microsoft and Cloudflare documentation read on 15 October 2026 and corrected after review the same day. Nothing was provisioned, no mailbox was connected and no mail was sent. Labels: **F** is a documented fact with its source, **I** is our inference, **R** is a recommendation, and **Unproved** needs a proof from the list below. Sources are linked at the end as [S#]. Settled architecture and product scope are unchanged; every sequencing and registration choice below is provisional and the user decides it.

## Answer in brief

- **(a) Drafts.** Use delegated Graph `POST /me/messages` with `Mail.ReadWrite`. It saves the draft in Drafts and does not send it; sending is a separate call [S1]. `Mail.ReadWrite` "does not include permission to send mail" [S5], but it does cover create, read, update and delete across the whole connected mailbox (see Permissions). **R:** don't request `Mail.Send`, so the consent screen and token show that ClearCase cannot send through Graph.
- **(b) Import.** Two paths need no extra Microsoft dependency: manual `.eml`/`.msg` upload, and delegated Graph import with `Mail.Read` and `GET …/$value` of messages the user picks in our UI. **R (provisional):** manual intake can come first and Graph import next, with the Outlook add-in deferred. **Open for the user:** whether Graph is in the alpha, and the registration topology. Nothing here picks a manual-only alpha.
- Imported material becomes files in a **submission** for the selected case, in the agreed client submission and manual FIFO processing workflow. It is not the operator results-import path, which is separate and unverified. Continuous sync is not adopted.

## Options compared

| | Manual .eml/.msg intake | Graph delegated, picked message | Outlook add-in (user selection) |
| --- | --- | --- | --- |
| Accounts | Any mail client | Work/school and personal MSA (Mail.Read/ReadWrite allow MSA consent) [S5]; shared mailboxes only work/school [S5][S6] | Outlook.com and Microsoft 365 mailboxes [S14]; multi-select Exchange only [S12] |
| Who picks mail | User, in Outlook "Save as/Download" as EML or MSG [S20] | User, in a ClearCase picker we build; an app rule, not a provider-enforced limit (see Permissions) | User, in Outlook itself; up to 100 messages [S12] |
| Bytes we get | File as saved by Outlook | `$value` MIME generated by Graph because "Outlook does not save messages in MIME format" [S3]: an acquired export copy, not the original wire bytes | `getAsFileAsync` returns Base64 EML, Mailbox 1.14, read mode [S13] |
| Client coverage | All | Any browser | 1.14 on web, new/classic Windows (M365, 2021+ retail, LTSC 2024), new Mac; **not** iOS/Android, LTSC 2021, classic Mac [S15] |
| Auth | Clerk only | Separate Microsoft OAuth connection, refresh tokens [S8][S9] | NAA via MSAL with `brk-multihub://` SPA redirect; legacy Exchange tokens are off in all M365 tenants [S16][S17] |
| Drafts | No | Yes, `POST /me/messages` [S1] | `displayNewMessageForm` or Graph via NAA (I) |
| Distribution | None | App registration and consent [S10][S11] | Admin deploy via Integrated apps, or public Microsoft Marketplace with certification policies [S18] |
| Effort / upkeep (I) | S / low (MSG parsing library to audit) | M / medium (OAuth, token store, picker, throttling) | L / high (manifest variants, client matrix, Marketplace) |

**I:** the add-in has the best "this email into this case" experience, but it adds a manifest, a second auth stack (NAA, SPA tokens that last 24 hours [S8]), a client-support matrix and per-tenant deployment. Graph import covers the same accounts with one server-side flow.

## Permissions and consent

- **F** [S5]:
  - Delegated `Mail.Read` "allows the app to read the signed-in user's mailbox". `Mail.ReadWrite` allows the app "to create, read, update, and delete email in user mailboxes. Does not include permission to send mail."
  - Both, plus `Mail.Send` and `Mail.ReadBasic`, have `AdminConsentRequired: No` and are consentable by personal accounts. `Mail.Read.Shared` and `Mail.ReadWrite.Shared` are "only valid for work or school accounts".
  - `Mail.ReadBasic` excludes body and attachments, so it can't import.
- **I:** these scopes cover the connected mailbox, not only the messages the user chose. The pages read show no per-message delegated mail scope. "Only the picked message" is **our app rule**: a ClearCase bug, leaked token or leaked secret could read every message, and with `Mail.ReadWrite` change or delete any of them, though not send through Graph.
- **F** [S7]: consent is recorded between a client and a resource, and a `.default` token request returns every scope already granted (example 3). **I:** requesting `Mail.ReadWrite` later is incremental consent: it adds a grant and narrows nothing. Once a user has granted it for drafts, ClearCase turning drafts off or "Disconnect" doesn't undo it; the user or admin must revoke it at Microsoft.
- **I:** credential IDs (secrets or certificates) don't isolate consent. Two instances sharing one client ID share one app identity and its grants. **R (not adopted):** use a separate client app for drafts, so import-only users never hold `Mail.ReadWrite`, and separate apps per client instance.
- **F** [S6]: shared or delegated mailboxes are read with `/users/{owner}/…` under the `.Shared` scopes, which don't support change notifications.
- **F** [S11]: by default users may consent to permissions that don't need admin consent, but Microsoft recommends tenants allow user consent only for verified publishers. **F** [S10]: since November 2020, with risk-based step-up enabled, users can't consent to unverified multitenant apps registered after 8 Nov 2020. Verification needs a Microsoft AI Cloud Partner Program account with a non-`onmicrosoft.com` publisher domain.
- **I:** expect admin consent in many work tenants. Every option except manual intake needs a consent step that the client's IT may own.
- **R:** request `openid profile offline_access Mail.Read` for import, and `Mail.ReadWrite` only when a user enables drafts. Never request `Mail.Send`. Add `.Shared` only for shared-mailbox users.

## OAuth, refresh, disconnect and Workers

- **F** [S9]: confidential web apps redeem the code at `/token` with a client secret or a certificate. Microsoft recommends certificates, and PKCE for all clients. **F** [S7]: `offline_access` is required for refresh tokens.
- **F** [S8]:
  - Refresh tokens last 90 days by default (24 hours for SPA redirects), "replace themselves with a fresh token upon every use", and old ones are not revoked, so the app must delete them.
  - A user or admin revoking refresh tokens revokes confidential-client tokens too.
- **I:** the code and refresh exchanges are form-encoded HTTPS POSTs, so plain Worker `fetch` is enough and MSAL isn't needed server-side. Signing a certificate client assertion would use Web Crypto. **Unproved** (P2).
- **F** [S19]: Worker memory is 128 MB and request bodies are capped at 100 MB on Free and Pro plans. Streams are recommended. **I:** stream `$value` and attachments into object storage rather than buffering them. Manual uploads of more than 100 MB need direct-to-storage upload.
- **R:** ClearCase's "Disconnect" deletes the stored refresh token and marks the connection revoked. It doesn't delete imported copies or revoke the grant, which stays a user or admin action at Microsoft. Treat `invalid_grant` as disconnected and stop retrying.

## Tenancy for the app registration (decision for GRS-86/GRS-91, not adopted)

`signInAudience` can be `AzureADMyOrg`, `AzureADMultipleOrgs`, `AzureADandPersonalMicrosoftAccount` or `PersonalMicrosoftAccount` [S21].

| Option | Isolation | Cost and upkeep (I) |
| --- | --- | --- |
| A. One GridShift multitenant+MSA app for all instances | One client ID, so shared consent and grants; per-instance credentials don't isolate them | One verification and consent identity; a leaked credential or bug spans clients |
| B. One GridShift multitenant+MSA app per client instance | Per-client client ID, credential, redirect URIs and consent | N registrations to verify, rotate and monitor |
| C. Client registers a single-tenant app in its own tenant | Strongest; client owns consent and revocation | Client IT effort; no personal accounts |

**R (not adopted):** option B matches the per-client isolation already chosen, with credentials as per-instance Worker secrets; a drafts-only app could be split off within it. The user decides the topology before anything is provisioned. Option C is an enterprise upsell, not a default.

## Identity, deduplication and versions

- **F** [S2]: default IDs change when an item moves. `Prefer: IdType="ImmutableId"` must be sent on every request. Immutable IDs survive folder moves in the same mailbox, but change when the item moves to an archive mailbox or is exported and re-imported. IDs are case-sensitive. `translateExchangeIds` migrates old IDs.
- **F** [S4]: `internetMessageId` is the RFC 2822 Message-ID, `changeKey` is "the version of the message", and `lastModifiedDateTime` is the last change.
- **I:** Message-ID is usually unique but not guaranteed, because senders set it. `$value` is generated on each request, so its bytes may differ between fetches. **Unproved** (P7).
- **R:**
  - Record stable provider IDs (tenant, mailbox, immutable ID), version metadata (`changeKey`, `lastModifiedDateTime`) and the SHA-256 of the acquired bytes. No single one of hash or Message-ID is the identity.
  - Dedupe retries safely: the same provider ID, version and hash is the same acquisition, so a retry can't create a second copy.
  - Keep versions. A changed `changeKey` or hash is a new version linked to the old one; nothing is overwritten.
  - Never auto-collapse by Message-ID. A matching Message-ID or attachment set never justifies merging a changed body; show it as a duplicate candidate for the user. Manual uploads use the Message-ID header and hash the same way.

## MIME and attachments

- **F** [S3][S22]: `GET /messages/{id}/$value` returns MIME. `$value` on an attachment returns raw bytes for file attachments, MIME for message item attachments, vCard for contacts and iCal for events. A reference attachment returns **HTTP 405** [S22].
- **F** [S23][S24]: types are file, item and reference (a link to OneDrive or other storage). `isInline` marks inline parts, and `fileAttachment` has `contentBytes` (Base64) and `contentId`.
- **F** [S1][S23][S25]: draft attachments under 3 MB use one POST. From 3 MB to 150 MB they need an upload session. S/MIME MIME drafts are limited to 4 MB.
- **F** [S26]: per app and mailbox the limits are 10,000 requests per 10 minutes, 4 concurrent requests and 150 MB of uploads per 5 minutes.
- **R:**
  - Store the whole `$value` as the acquired original, and derive attachments from it so inline and item parts stay together.
  - **Reference attachments are not imported.** A 405 means ClearCase holds a name and URL, not the content. Show it prominently as "pending/external: content not imported" and ask for a manual copy of the content or a separately authorized connector. No `Files.*` scopes are approved. We don't assume a cloud link is a file copy.
  - Until accepted attachment contents are preserved and viewable, a candidate can't claim file-viewing readiness.
  - Download with raw `$value` rather than the Base64 `contentBytes` JSON. Keep concurrency at most 4 per mailbox, and honour 429 with `Retry-After`.

## Durable originals, fidelity and provenance

**R:** each imported message becomes a submission file holding the acquired bytes exactly as received (`.eml` from Graph or the add-in, or the uploaded file) and a provenance record: method (graph, add-in or upload) and account type; tenant ID and mailbox address; immutable ID, Message-ID, `changeKey` and receivedDateTime; fetchedAt and the importing ClearCase user; SHA-256 and size.

The bytes, hash and provenance are never altered; derived text and previews are separate. **Fidelity limits:** a Graph `$value` is a provider-generated export [S3], so the hash proves what ClearCase acquired, not what the sender's server put on the wire, and ClearCase says so wherever the file is shown. Disconnecting a mailbox, deleting the source or revoking consent must not change the stored file. **I:** a deleted source then returns 404 on re-fetch, and ClearCase shows "source no longer available", never a removal. **Unproved** (P4). Access follows case assignment in the client instance, and the mailbox owner's Microsoft access grants nothing extra.

## Safe previews

User-confirmed: every accepted file is viewable in the app, with download optional. **F** [S27]: Graph strips "potentially unsafe HTML (for example, JavaScript)" from `body` by default, unless the request sends `Prefer: outlook.allow-unsafe-html`. **I:** stored MIME and uploaded files bypass that cleanup, so ClearCase must treat all mail HTML and every attachment as untrusted. **R:**

- Show each accepted file in the app, under the same case permissions as the submission, through a dedicated safe viewer for its format or a sanitized derived preview. The stored original stays unchanged.
- Never execute active content: scripts, macros, embedded objects or remote loads.
- Mail HTML: server-side sanitize to an allow-list; render in a sandboxed iframe with no `allow-scripts` or `allow-same-origin`, on an origin without cookies, under a strict CSP; block remote images by default; resolve `cid:` parts only from the stored MIME.
- A format with no safe viewer or derivative isn't yet viewable. That is a readiness gap, not a reason to serve it inline. Download stays an option, never the only view.

## Drafts without false "sent" claims

- **F** [S4]: `isDraft` is true while a message "hasn't been sent yet". **F** [S2]: a draft created with immutable IDs keeps its ID after sending, and the same ID returns the Sent Items copy, which "might not succeed immediately" because the copy is created only once the send succeeds. **I:** `isDraft=false` alone doesn't prove the mail was delivered or even sent; it says only that the item is no longer a draft. The same holds when the user sends from Outlook. **Unproved** (P8).
- **R:** ClearCase keeps the observed status labels and nothing stronger:
  - "Draft created in your mailbox" after the 201;
  - "Draft still in Drafts" while `isDraft=true`;
  - "No longer a draft in your mailbox" when `isDraft=false` was observed, with no delivery claim;
  - "Seen in Sent Items" only when the Sent Items copy was actually found by the same immutable ID [S2], still with no delivery claim;
  - "Draft no longer found" on 404.

  It never claims ClearCase sent anything. Drafts open in Outlook via `webLink` [S4].

## Optional continuous sync (unexplored scope)

**F**: delta query is per folder, with `@removed` entries for deletions [S28], and change notifications aren't supported on `.Shared` scopes [S6]. **I:** sync needs standing refresh tokens, schedulers, per-folder state, retention rules for mail nobody chose, and broader privacy review. **R:** consider it only if users show that manual selection misses case-relevant mail.

## Licensing, cost and platform risk

- **F** [S29]: the metered-API list has no mail endpoints. **I:** so there is no documented Graph metered fee for mail calls. That isn't zero overall cost: mailbox licences, tenant and provider policies and throttling [S26] still apply, and none is costed here.
- **F** [S10][S18]: publisher verification needs a Cloud Partner Program account (cost not checked), and Marketplace listing requires the certification policies.
- **F** [S30]: EWS is being disabled in Exchange Online from October 2026, and its replacement is Graph. **R:** use no EWS. The add-in multi-select APIs refer to EWS-format item IDs [S12]; that is a format, not an EWS call (I).
- **I:** the Cloudflare cost is bounded by storage and Worker requests, and the add-in adds Marketplace or admin-deployment overhead per client.

## Synthetic acceptance proofs required before implementation

P1–P11 are all **UNRUN**. Each uses synthetic mail in a Microsoft test tenant and test MSA, both still to be obtained, at an exact SHA:

- **P1 Isolation.** Two instances and two cases. An import into case A is invisible to case-B users and to the other instance, and one instance's tokens and credentials are unusable from the other.
- **P2 Workers OAuth.** Auth code with PKCE and offline_access, for work and MSA accounts, on a deployed Worker preview rather than `wrangler dev`. Refresh rotation stores the new token and deletes the old one.
- **P3 Revoked connection.** User or admin revocation leads to `invalid_grant`, the state "disconnected", no retry storm, and imports still readable.
- **P4 Source moved or deleted.** Move a message to another folder and confirm the immutable ID is stable. Archive and delete it, then record the behaviour. The stored hash is unchanged.
- **P5 Duplicate, retry and versions.** Import the same message twice, from two folders and as an `.eml` upload, and kill the download midway. Edit a draft between imports. Expect an idempotent retry, a duplicate candidate shown, no auto-collapse by Message-ID, and the edit kept as a new version.
- **P6 Attachments.** Use file, inline image, attached message, reference link, a file over 3 MB and one of about 25 MB. Attachment hashes match the MIME parts, each accepted file opens in the in-app viewer, and the reference shows "pending/external: not imported".
- **P7 MIME stability.** Fetch `$value` twice and compare hashes, noting any byte differences. This shows how far the hash can support retry idempotency; it never makes hash or Message-ID the sole identity.
- **P8 Drafts.** The token `scp` lacks `Mail.Send`, and a `/send` probe gets 403. Create a draft with an attachment over 3 MB. Send it from Outlook by hand and check the labels follow the observed `isDraft` and the Sent Items lookup, with no delivery claim. Delete a draft and check it shows "no longer found".
- **P9 Hostile content.** Use a synthetic `.eml` with script, `onerror`, a form, CSS `url()`, remote images and hostile attachments. Nothing runs, and no network request leaves any preview or viewer.
- **P10 Shared mailbox.** A work user with full access imports via `.Shared`, and an MSA can't consent to it.
- **P11 Throttling.** Inject 429 with `Retry-After`. Concurrency stays at or below 4 per mailbox.

## Unproved and open

All of P1–P11; how to get a test tenant; CPP verification cost; the registration topology (the user decides); whether Graph is in the alpha (the user decides); a safe viewer or derivative for each accepted attachment format; how reference-attachment content reaches ClearCase; an audited `.msg` parser for [MS-OXMSG] [S31]; add-in install for personal Outlook.com users outside Marketplace; and the new Outlook "Save as" behaviour, which Microsoft Q&A threads (not primary sources) report as uneven.
