# Hosted results storage and protected originals (GRS-115)

The hosted `CaseReader` and `AssetsAccess` over one client's D1 database and private R2 bucket, the D1 migration, and the storage-level helpers that the client upload controller (GRS-28) and the operator candidate import controller (GRS-30) call. Words follow [GLOSSARY.md](../../GLOSSARY.md). The layout follows the GRS-109 probe ([storage proof](../acceptance/hosting/storage.md)); the differences are listed below.

**Status: PREPARED, UNVERIFIED.** The unit tests in `tests/hosted-foundation/storage/` run the adapters against test doubles (D1 over `node:sqlite` with the real migration, R2 in memory). They are not evidence of Cloudflare D1 or R2 behaviour, limits or latency, nor of local workerd. Nothing here is composed into `hosted/services.ts` yet, so production still answers 503.

## Rules

- **Client.** `clientId` comes from trusted deployment configuration only. Before any read or write, the storage gate checks that `rs_storage_identity` and the bucket's `identity/client.json` both name it. A missing, malformed or other-client identity refuses everything with `storage-unavailable` or `asset-unavailable`, and never names the other client. A missing binding, client id or budget refuses in the same way.
- **Results.** A version is `staging` until one guarded batch checks every count and stores it. A stored version is immutable. Clients reach it only as the exact published version of its case. A candidate (stored but not published), a staging version and a withdrawn version are refused with `forbidden`. A Keep mark (`keep = 1`) never changes that. A withdrawal binds even if a stale publication pointer still names the version. Version reads authorize, check the publication, and then authorize and check it again before they return.
- **Originals.** Originals are case-level inputs and are reachable through the case grant (`read-original`), with or without a publication. Each original is content-addressed (`orig/<sha256>`) and written once, by a conditional R2 put (`onlyIf: etagDoesNotMatch '*'`) after a look: matching bytes are a no-op, and any other bytes are a conflict, never an overwrite or a delete. An asset id binds to exactly one original. **A case binds an original only through its own upload.** `declare` records the upload (`declared`), `put` carries bytes that hash to the declaration and records `stored` for that operation, and `finalize` refuses any operation that is not `stored`, so naming a hash that another case uploaded binds nothing. A `finalize` without an own `put` answers `digest-mismatch` (the same answer as for a body that does not match), and `put` answers `repeated: false` unless this very operation already stored its bytes, so no answer tells a case whether another case holds the same bytes. The physical key stays `orig/<sha256>` (one object per distinct content in the client's bucket); a case-and-asset-bound key was not adopted because the existing tests address `orig/<sha256>`. The residual is stated under Not done. Every delivery reads the whole object, rejects a size mismatch before downloading, hashes it, authorizes again and records the delivery before any byte leaves. A missing object answers `missing-original` and a changed one `changed-original`, each recorded as `failed`. One `bytes=` range returns 206 from the verified bytes. Several ranges, a range past the end or a backwards range return 416 with no body, and HEAD has no body. Every response is `attachment`, `nosniff`, `private, no-store` and `sandbox; default-src 'none'`, so original content never runs with the app's privileges. The `Content-Disposition` is the serve policy's own `attachment` form (`servePolicy(...)`, forced to download): path cut, controls and bidirectional overrides replaced, a length cut, an ASCII `filename=` fallback and an RFC 8187 `filename*` that also encodes the apostrophe. It is built before the delivery is recorded. Declaring a filename with controls or bidi overrides is refused (`invalid-declaration`). The links contract returns `viewerHref: null` unless the composing parent supplies `viewerRoute`; a returned path is used only under `/cases/<case>/`.
- **Previews.** `preview/<version>/<sha256>` objects with `rs_preview` rows are reachable only while their exact version is published and not withdrawn. Nothing writes previews yet.
- **Keys.** Object keys are built only from validated digests (`orig/`, `pkg/<version hex>/<sha256>`, `preview/<version hex>/<sha256>`), never from a filename, a package path or request text.
- **Import staging.** `stage` checks the budgets, verifies the exact package bytes with `verifyCandidateBytes`, requires the manifest's `case.id` to be the target case, and **derives the canonical projection from those bytes** with the hosted-safe projector (`projectPackage`, which runs the package validator on the bytes and the same read model as `local-case/project.server.ts`). The caller's projection is a claim: any difference in documents, assets, seeds, chronology, overview or counts refuses the import (`inconsistent-projection`), and only the derived projection and its digest are stored. The overview's import-diagnostics counts are the package-level validation's, since the case-folder checks are the import controller's. **Original status comes from verified per-case facts, never from the claim** (`original-facts.ts`, the hosted counterpart of `verifyOriginals`): for each file asset, the case's own finalized original under that asset key (`rs_case_original` joined to a finalized `rs_original_upload` of the same case, asset and bytes) is read; its `filename` is the original's real case-relative path. An exact name is `verified`; a name equal after NFC and lower-casing, with no other original of the case folding to the same path, is `case-mismatch` recorded with the real name; no association, another name, or an ambiguous fold is `unavailable`, as the local projector reports an original the case folder does not hold. The association's SHA-256 and size must be the indexed ones, and the R2 object (under `orig/<sha256>`) is read whole and hashed: an object absent from R2 is `unavailable`, while bytes that are not the indexed ones, an object changed at rest or a foreign object key is a genuine mismatch and refuses the import as `integrity` (never relabelled `verified`). The first 1,024 bytes are sniffed with the local `contentContradictsType`, which sets download-only. Another case's association, another asset key, or a hash that exists only globally in `rs_original` or `orig/<sha256>` is not a fact. A claim that differs (including a claimed `verified` for an original this case never uploaded) is refused as `inconsistent-projection`, and the package's supplied asset ids, source hashes and warnings are unchanged. `stage` checks the quota and the case before it reads originals, so an over-quota or repeated stored import costs no R2 read, and reads each distinct original once. It then writes the version row, the package-file rows, the objects (write-once), and the document, asset and seed rows in guarded batches of at most `maxRowsPerBatch`. A failed attempt stays `staging` and is never served. A retry deletes the old attempt's rows in the same batch that starts a new attempt. `stage` never publishes.
- **Upload intake.** `declare` records the upload before any byte is written, so an object never exists without a row that traces it. `put` refuses bytes that do not match the declaration. `finalize` hashes the stored object whole and binds the original in one guarded batch. Repeated calls are idempotent per `operationId`.
- **Authorization of mutations.** Every writer takes `authorize(m: StorageMutation)`, storage's own typed capability request: `{ clientId, caseId, capability: 'original.upload' | 'results.import', step: 'declare' | 'put' | 'finalize' | 'stage', operationId }`, with `clientId` the deployment's trusted client. It is asked first, before the storage gate is read and before any row or object is touched. A missing callback denies (`forbidden`), a refusal is rethrown, a callback that resolves `false` denies, and a callback that fails is `storage-unavailable`, never an allow. `CaseOperation` is unchanged; the composition adapts `authorize` to the identity service's capability check (GRS-114). The upload and import controllers stay separate and each builds its own factory; there is no export that writes without the callback.
- **Budget invariants.** `storageBudgets` refuses a set whose `maxOriginalBytes` exceeds `maxBufferedObjectBytes` or whose `maxPackageFileBytes` exceeds `maxPackageBytes`, and every writer checks the same relations on a raw object, so no body is stored that `finalize` could never verify.
- **Cumulative quotas.** The writers reserve in D1 before any R2 write. `declare` is one conditional `INSERT … SELECT` that inserts only while the case's upload count, the case's declared bytes and the client's declared bytes stay within `maxUploadsPerCase`, `maxOriginalBytesPerCase` and `maxOriginalBytesPerClient` (`over-quota` otherwise); a repeat of the same operation reserves nothing. `put` spends one of `maxPutAttemptsPerUpload` with an atomic `UPDATE … RETURNING` before the bucket is touched, and an operation that already stored its bytes never reaches the bucket again. `stage` makes the version row's batch conditional on a free version slot (`maxVersionsPerCase`), free package bytes (`maxPackageBytesPerCase`, `maxPackageBytesPerClient`) and a free attempt over the case (`maxStagingAttemptsPerCase`, retries included); a retry needs only an attempt. A missing or invalid quota makes every mutation `storage-unavailable`. Abandoned reservations are never released (nothing here deletes or reaps), so they keep counting. This bounds what an authorized writer can accumulate through these helpers; it is **not** a hard all-in cost cap, and it does not meter unauthenticated edge traffic or provider billing lag.
- **Verified load of the read model.** Before a stored version's document or seed rows are served, the reader loads the version's rows once, checks their counts and recomputes the read-model digest against the version's `read_model_sha256`; a changed, added or dropped row fails with `integrity`. `verifyVersion` additionally verifies the package bytes against the version's identity and derives the read model from them again, so rows rewritten together with their stored digest also fail. A version should be verified before it is published (GRS-31).
- **Original facts at verification.** `verifyVersion` reads this case's original facts again (D1 association and R2 bytes, hashed now). Every stored asset row that claims `verified` or `case-mismatch` must still equal its current fact exactly (real name, fingerprint, download-only), otherwise the version is `ok: false` (`integrity`); a row that claims `unavailable` asserts nothing and is kept as stored, so an original uploaded after an honest import does not make an immutable version unverifiable. The model is then derived from the package bytes under exactly those facts and its digest compared. Rows and digest rewritten together to call a never-uploaded original verified therefore fail.

## Differences from the GRS-109 layout

- The chronology list is stored per document in D1 (`rs_document.list_json`), not as `rm/<version>/chronology.json` in R2. A document page and the list cost one D1 statement each. The list's D1 read size at v5 scale (about 1.5 MB) is not measured.
- Package-file keys are content-addressed within their version, not path-addressed.
- The migration is unreleased, so `0001` was edited in place for this fix round (the `rs_original_upload` provenance state and attempt count, `package_bytes`, a case index); a database that already applied the earlier `0001` needs a new migration instead.
- Objects larger than `maxBufferedObjectBytes` are refused (`asset-unavailable`), not served through the probe's two-read stream. A larger original needs that streaming path, which is not implemented here.
- The storage gate is cached per `createCloudResults` call, not per isolate. If the composition creates it per request, the gate costs one D1 statement and one R2 GET per request.

## Handoffs for the original facts (parent, unverified here)

- **The real name is the declared `filename`.** The upload controller (GRS-28) must declare each original under its package asset key (`assetId`) with the case-relative path as `filename` (at most 255 characters, no controls). An original declared under another key or with an unrelated name is `unavailable`; it is never guessed to be present. The hosted import controller (GRS-30) supplies no status; its claimed projection is only compared.
- **Cost at v5 scale is unmeasured.** `stage` and `verifyVersion` read and hash every referenced original (bounded by `maxBufferedObjectBytes`, 8 at a time, one read per distinct SHA-256) and issue one D1 query for the case's associations. The Workers subrequest and CPU limits for 1,689 originals, and R2 behaviour, are UNRUN; a measured plan (for example verifying in batches across requests) belongs to the integration owner.
- **No migration change.** The existing `rs_case_original`, `rs_original`, `rs_original_upload` columns carry every fact; `0001` is unchanged by this correction.

## Not done here


- Publication and withdrawal writes (GRS-31), user-work revision and storage (GRS-117), the audit sink (GRS-116), the upload and import routes and their authorization (GRS-28, GRS-30), and preview generation.
- A reaper for `declared` or `stored` uploads whose object never finalized, and for objects of abandoned `staging` attempts. There is no destructive cleanup, no retention action and no provider cleanup here.
- Case-bound physical keys. Provenance is per case and per operation in D1, but the object under `orig/<sha256>` is shared by every case of the client that uploaded the same bytes; a case holding the bytes can find that their object exists only by uploading them itself, and no response reveals another case's upload. A key per case and asset would also separate the bytes and cost storage per upload.
- Per-document indexed reads. The verified load reads a version's rows once per reader, so a reader built per request reads the whole model once per request (about 1.5 MB of list data at v5 scale, unmeasured). Reading one document by index after a verified load, and the per-isolate cache of a verified version, remain follow-ups.
- Several ranges, an unknown range unit and a range past the end answer 416, as before; RFC 9110 allows serving 200 for these. The behaviour is documented, not changed.
- The D1 double runs the real migration on `node:sqlite`; Cloudflare D1's batch, foreign-key, statement-size and parameter limits, its `RETURNING` support, its error text (which `isConstraintFailure` would match) and R2's conditional put are not exercised.
- Real D1/R2/workerd legs, numeric budgets and EU placement (see [What stays HOLD](../acceptance/hosting/storage.md#what-stays-hold)).
