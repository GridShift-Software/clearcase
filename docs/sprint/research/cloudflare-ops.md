**What a sandbox deploy does** (from `docs/acceptance/hosting/workers-dev-bootstrap.md`, `deploy/native-alpha/*.ts` and `status.md`):
1. `bun run --bun build:hosted` (`scripts/pilot/hosted.ts`: vite build with the Cloudflare adapter, stamps HEAD, writes `.svelte-kit/cloudflare/_worker.js` and assets).
2. Stage: `workers-dev-bootstrap.ts` writes `client-a.wrangler.json`, `client-b.wrangler.json`, `staff.wrangler.json` plus `bootstrap.json` (hashes, pins, argv). `runtime-config.ts` plans vars from a `runtime-config-input-*.json` (e.g. `runtime-config-input-20261027-v5-b.json`): `CLEARCASE_CLIENT_ID`, `CLEARCASE_APP_ORIGIN`, `CLEARCASE_NATIVE_CONFIG` (<= 5000 bytes), Clerk sign-in URLs; secrets by name only. `PLACEMENT_REGION=aws:eu-west-2` adds the `placement` key (971230f1).
3. Bundle proof and settings check (artifact sha256 recorded in status).
4. `wrangler d1 migrations apply` per client, with a D1 Time Travel bookmark taken before each.
5. `wrangler deploy --config <client>.wrangler.json` under real Node with a sanitised env (`CLOUDFLARE_LOAD_DEV_VARS_FROM_DOT_ENV=false`, `CLOUDFLARE_INCLUDE_PROCESS_ENV=false`). Secrets (`CLERK_CLIENT_SECRET_KEY`, `CLERK_CLIENT_JWT_KEY`, `CLERK_STAFF_*`) are put out of band once per Worker and survive redeploys.
6. Smoke: `/health`, `/sign-in`, `/sign-in/operator` 200; `/cases` 401. Placement checked on `cf-placement: remote-LHR`.

`fast-deploy-b.sh`, named in `status.md`, is **not in the repo, `.local` or `orch-bin`**; it lived in the retired orchestrator session. S0 must recreate it as a committed script.

**Duration.** The upload itself is quick: each version is created about 1.5 s before its deployment, and status records "deployed to B then A at 08:50 to 08:52" (about 1 min per Worker from a built artifact). Build about 1 to 3 min, migrations and proof 1 to 2 min, so a cold deploy is about 5 to 8 min; the day-long gaps between deploys on 27 Oct were gates and reviews, not deploys.

## 2. Clerk

Three **development** instances (status 27 Oct, `follow-ups.md` 131): client A, client B and staff. The owner account `admin@gridshift.co.za` (and `admin+clerk_test@`) exists in all three; colleagues share it. Per deployment (`docs/hosted-foundation/identity.md`): vars `CLERK_CLIENT_PUBLISHABLE_KEY`, `CLERK_CLIENT_SIGN_IN_URL`, `CLERK_STAFF_PUBLISHABLE_KEY`, `CLERK_STAFF_SIGN_IN_URL`, `CLEARCASE_APP_ORIGIN` (the only accepted `azp`); secrets `CLERK_CLIENT_SECRET_KEY`, `CLERK_CLIENT_JWT_KEY` (RSA-2048 PEM, the "JWKS Public Key" on the instance's API keys page, used for networkless `verifyToken`), and the staff trio. Allow-lists are **exact URLs**: the client instance needs `https://<origin>/sign-in`, the staff instance `https://<origin>/sign-in/operator`, per origin. A missing entry is not refused: Clerk falls back to the instance home URL (seen live 27 Oct, staff on B landed on A).

Clerk docs (clerk.com, read 28 Oct): development instances are capped at 100 users, carry a "Development" banner, use `accounts.dev` for the Account Portal and pass the dev browser as `__clerk_db_jwt` in the query (so any origin can complete sign-in). The redirect allow-list is managed in the Dashboard or by `POST /redirect_urls` (`clerkClient.redirectUrls.createRedirectUrl({ url })`), full `https://` URLs; no wildcard is documented. Clerk recommends development keys for host-provided preview domains ("not possible to use production API keys" there) and a separate Clerk application for staging. Session token refreshes every 60 s; maximum session lifetime defaults to 7 days and inactivity timeout is off by default (both on the Sessions page; custom values are free in development, paid in production); custom claims under 1.2 KB. `authorizedParties` (`azp`) should always be set.

**New staging instance:** one Clerk application `clearcase-staging` (development instance) replacing A, B and staff for the demo, or two if staff must stay a separate issuer (the code requires a different application for staff). Needs: publishable key, secret key, JWKS public key, the Sessions page set to 8 h max lifetime (optional, since the app session is ours), test users with `+clerk_test` addresses (code 424242), and allow-list entries `https://clearcase-staging.shiny-sunset-211d.workers.dev/sign-in` and `/sign-in/operator`.

**One dev instance for staging plus previews: yes.** Users are shared (100 cap is fine), the dev browser flow accepts any origin, and each preview only needs (a) its two exact allow-list entries, added by the preview script through `POST /redirect_urls` with the secret key, and (b) `CLEARCASE_APP_ORIGIN` set to `https://<preview>-clearcase-staging.shiny-sunset-211d.workers.dev` via `wrangler preview --var`, because the runtime refuses an origin that differs from `azp`. Preview names must be sanitised (`sprint/S5-shell` -> `--name s5-shell`).

## 3. Cloudflare Access on `*.workers.dev`

Yes. Since December 2025 a Worker can be protected at the Worker level, covering its workers.dev hostname and all Preview URLs, so no zone is needed. Prerequisite: Zero Trust enabled on the account (team name, Free plan up to 50 users; the onboarding still asks for payment details and does not charge). Steps: (1) **owner**: Cloudflare dashboard > Zero Trust > choose team name, Free plan, payment details; (2) **owner or agent**: Zero Trust > Settings > Authentication: leave One-time PIN on, or add Google; (3) **agent**: Workers & Pages > `clearcase-staging` > Access tab > "Protect this Worker behind Access" > *All traffic* (previews and staging) > policy: Email domain `gridshift.co.za` plus named emails for Dion and Carlo if elsewhere > session 24 h > Apply; or by API `POST /accounts/{account}/access/apps` with destination `worker` (or `preview_worker` for previews only) and `worker_id`. (4) Astra proves: unauthenticated GET redirects to the team login; after the PIN, `/health` 200 and Clerk sign-in completes (Access checks before the Worker, so the Clerk callback GET passes once the Access cookie exists). Caveats: Access cookies are per hostname, so each preview URL asks for a PIN once; WebSockets are refused by Worker-level policies; `ctx.access` is not forwarded through the static-assets router (not needed). Seats: one per authenticating user, 50 free.

## 4. Colleague access (Dion and Carlo)

Recommended, least privilege and fastest, all agent-doable except the Access login:
- **Deploys and previews from their machines:** one account-scoped API token each (dashboard > Account API tokens > custom: Workers Scripts Edit, Workers KV Storage Edit, D1 Edit, Workers R2 Storage Edit, Account Settings Read, Workers Tail Read; scope to this account only; 30-day expiry). They export `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`; Wrangler needs no login and no account membership. Account membership (Workers Platform Admin) is the fallback if a token cannot create previews; CI-only deploys would block the per-ticket preview loop.
- **Access login:** their emails in the Access policy; One-time PIN, no Cloudflare account needed.
- **Clerk:** invite both to the Clerk workspace as members (free), or simply hand over the `+clerk_test` user list; test users sign in with code 424242. The secret and JWT keys stay in Worker secrets, never in chat.
- **R2 loading:** one R2 Object Read & Write token scoped to `clearcase-staging-files`, endpoint `https://<account>.eu.r2.cloudflarestorage.com` (EU jurisdiction bucket), for rclone/S3. Expiring date set.

## 5. Runbooks (O = owner, A = agent)

**(a) Create staging**
1. A: `wrangler d1 create clearcase-staging-db --jurisdiction eu`; record the UUID. 2. A: `wrangler r2 bucket create clearcase-staging-files --jurisdiction eu`. 3. A: `wrangler kv namespace create SESSIONS` (revocation keys); record the id. 4. A: commit `deploy/staging/wrangler.jsonc`: `name: clearcase-staging`, real `account_id`, `main`/`assets` to the build output, `compatibility_date 2026-10-12`, `nodejs_als`, `vars` (`CLEARCASE_CLIENT_ID=staging`, `CLEARCASE_APP_ORIGIN=https://clearcase-staging.shiny-sunset-211d.workers.dev`, Clerk sign-in URLs), `d1_databases[DB]` with `migrations_dir`, `r2_buckets[BUCKET]` jurisdiction `eu`, `kv_namespaces[SESSIONS]`, `placement: { region: "aws:eu-west-2" }`, `workers_dev: true`, `preview_urls: false`, and an empty `previews: {}` placeholder. 5. O or A (owner's Clerk login): create the Clerk application, read the three keys, add the two allow-list entries, create test users. 6. A: `bun run --bun build:hosted`, `wrangler d1 migrations apply clearcase-staging-db --remote -c deploy/staging/wrangler.jsonc`, `wrangler deploy -c deploy/staging/wrangler.jsonc`. 7. A: `wrangler secret put CLERK_CLIENT_SECRET_KEY|CLERK_CLIENT_JWT_KEY|CLERK_STAFF_* -c ...` (values pasted by the owner into the prompt, never into a file). 8. Access per section 3 (O for Zero Trust enablement). 9. A: smoke the four routes and `cf-placement: remote-LHR`; record the SHA and version id in `status.md`.

**(b) Enable previews**
1. A: fill `previews` in the same config: repeat `vars` (minus `CLEARCASE_APP_ORIGIN`, passed per preview), `d1_databases`, `r2_buckets`, `kv_namespaces`, `placement` pointing at the staging resources (a top-level-only binding is undefined inside a preview). 2. A: `wrangler preview base-config secret put` for each Clerk secret (new previews inherit them). 3. A: `scripts/preview.sh`: `name=$(git branch --show-current | tr '/_' '--' | tr A-Z a-z)`; `bun run --bun build:hosted`; add the two Clerk allow-list URLs for `https://$name-clearcase-staging.shiny-sunset-211d.workers.dev` through `POST /redirect_urls` if absent; `wrangler preview -c deploy/staging/wrangler.jsonc --name $name --var CLEARCASE_APP_ORIGIN=https://... --json`; print the Preview URL. 4. Access "All traffic" already covers it. 5. On PR merge: `wrangler preview delete --name $name` (limits: 500 previews per Worker on Paid, 100 deployments per preview; stale ones are evicted least-recent first). Previews share the staging D1, R2 and KV: schema changes must be additive and applied to staging first.

**(c) Deploy staging on merge**
Option 1, GitHub Actions on the pc1 runner (`docs/ci-runner.md`): add a `deploy-staging` job to `ci.yml` on `push: branches: [sprint/hosted-demo-20261105]`, `runs-on: [self-hosted, Linux, X64, clearcase-pc1]`, steps: checkout (pinned), setup-bun, `bun install --frozen-lockfile`, `bun run --bun build:hosted`, `bunx wrangler d1 migrations apply ... --remote`, `bunx wrangler versions upload -c deploy/staging/wrangler.jsonc --tag $GITHUB_SHA`, `bunx wrangler versions deploy <id>@100% -y`, smoke; secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository secrets (O adds them; the runner's admission hook admits pushes to one branch only, so it needs a one-line policy change for the sprint branch). `cloudflare/wrangler-action` is not in the allowed actions list, so use `bunx wrangler`. Option 2, faster to start: the orchestrator runs the same five commands from a committed `scripts/deploy-staging.sh` after each merge and records the SHA and version id. Start with option 2 today, move to option 1 when the token exists.

**(d) Client production instance later**
1. O: zone `active` on Cloudflare (registrar nameservers), production Clerk instance for the client on its own domain, production keys. 2. A: `d1 create <client>-db --jurisdiction eu`, `r2 bucket create <client>-files --jurisdiction eu`, `kv namespace create`. 3. A: add an `env.<client>` block (or a per-client config file) with `workers_dev: false`, `preview_urls: false`, `routes: [{ pattern: "<client>.clearcase.co.za", custom_domain: true }]`, London placement, `CLEARCASE_APP_ORIGIN=https://<client>.clearcase.co.za`. 4. A: migrations, `versions upload --env <client>`, `versions deploy` at 10% then 100%; `secret put`. 5. O/A: Clerk allow-list for the two callbacks; Access off (clients) or on for internal instances. 6. Load data by rclone to the client bucket, run the S4 builder, publish. 7. Record SHA, version id and rollback version in `status.md`.

**(e) Rollback**
1. A: `wrangler versions list -c <config>`; `wrangler rollback <previous-version-id> -c <config> --message "<reason>"` (seconds; keeps bindings and secrets). 2. If a migration broke data: `wrangler d1 time-travel info <db>` then `wrangler d1 time-travel restore <db> --bookmark <pre-migration bookmark>` (bookmark recorded in step 4 of every deploy; 30-day window on Paid). 3. Previews: redeploy the branch or `preview delete`. 4. Custom domain regression: redeploy the `workers-dev` origin config first, then unbind the domain (status 73). 5. Smoke the four routes and record the SHA in `status.md`.
