## ARCH-01 / D1 — case ownership of PDF builder state

**Why it survives challenge.** `src/lib/views/bundles/builder.svelte.ts:5-9` exports one module-level builder, document map and blob map. The consuming `Builder.svelte:16` receives the case's header and bundles but no case/session identity. The ordinary route through `src/routes/v/[vid]/+layout.svelte:15` and `src/routes/cases/+page.svelte:23` uses internal links without a forced reload. Component remounting does not create a fresh imported module. No case-change reset was found in the callers.

The apparent navigation mitigation is for **header edits**, not builder ownership: `court_bundle_tab/+page.svelte:107-109` only prompts when the header changed or a header action failed. It neither clears nor keys the builder. Its `Builder` invocation at line 134 has no ownership argument. `Builder.svelte:44-50` clears builder inputs only on an explicit user operation; starting from a saved definition also clears the output, but neither action is required when entering another case.

The save chain is concrete: `Builder.svelte:110-124` derives saved metadata from the retained output; `post.ts:12` sends it to `?/save`; `court_bundle_tab/+page.server.ts:94-106` obtains the case from the current results-version URL. A user who builds in A, navigates to B, and then clicks Save can persist A's item list in B. The output's blob remains available in the same browser session; this is not a server upload of the PDF. Rebuilding with B's header and A's retained selections is a separate reachable contamination path.

**Correction.** A fetch already dispatched while on A does not retarget to B after navigation. The request URL is resolved when `fetch` is called, before its first await. The valid asynchronous concerns are assembly finishing into shared state after navigation, and save completion/reload/navigation callbacks acting on a changed UI. Do not claim an already-sent A save necessarily writes to B. Nor does this establish a cross-user or hosted authorization leak: inputs are user-selected files in one local browser session.

**Priority and proof.** Retain P1 because ordinary multi-case navigation can present and save the wrong evidence selection. Prove A → B → A using the real built app, distinguishable synthetic PDFs and separate case identities. Check persisted case IDs, item lists and output bytes/header. Exercise navigation during file reading, assembly and save separately, with the save request's actual URL recorded. Preserve intended same-case navigation and explicitly decide how results-version changes affect a draft. A fix must bind asynchronous completions as well as visible state; merely resetting component props is insufficient.

## ARCH-02 — same-named source folders become one case

**Why it survives challenge.** `case-pack.server.ts:104-107` computes a lossy slug. At lines 223-230, the resolved source folder's basename supplies the ID, while the operator's label supplies only `caseLabel`. `service.server.ts:210-222` sends that prepared package directly to `importPackage`; it has an import-in-progress guard but no new-case/existing-case identity choice.

The strongest counterargument is the existing source-root refusal. It does not cover this trigger: `service.server.ts:285-290` first looks up **resultsVersion**, and rejects a different root only when that exact version already exists. Different accepted content with the same derived case ID gets a distinct results version and bypasses this comparison. The filesystem extraction checks prevent overwriting another pack at one extraction destination; they do not distinguish two pre-existing source directories with matching basenames. Use different contents and valid source/destination paths when reproducing; identical content may hit the existing-version refusal and is not the right diagnostic.

The consequences follow the shared ID: `service.server.ts:163-174` groups the case list by case ID, `user-work.server.ts:145-158` scopes register rows by it, and `store.server.ts:159-169` updates the active pointer by it. Label differences do not create a namespace boundary. Notes and overlays have additional anchor/seed rules, so do not claim that every individual anchored record will automatically attach successfully to every unrelated document.

**Correction.** Import stores a candidate and returns (`service.server.ts:319-325`); it does not itself activate it. The second explicit activation changes the pointer for the shared ID. Previously imported package bytes are not thereby replaced, and case-folder originals are untouched. “Merges case identity and exposes shared case-scoped user work” is supported; “silently overwrites the first case's originals on import” is not.

**Priority and proof.** Retain P1: unrelated folders can become one logical case without explicit user consent. Run two accepted synthetic imports from distinct parents with identical basenames and different content, then examine case listings, candidate previews, activation pointers and register visibility before and after explicit activation. Include different display labels, slug collisions and a legitimate repeat update. An immediate refusal on conflicting root identity is defensible, but a full fix must distinguish a new case from an intentional move/relink/update; it must not silently renumber existing cases or orphan their user work.

## D2 — deletion of a newer register row from a stale view

**Why it survives challenge.** `RegisterPage.svelte:273` submits `rowId` and confirmation, without the displayed `version`. Its enhanced delete handler at lines 98-109 confirms locally and refreshes **after** the write. `ConfirmDelete.svelte` and `confirm-delete.ts` bind confirmation to the row ID, not the row's revision. No cross-tab refresh mechanism was found in this path. The action checks confirmation (`page.server.ts:123-133`), then calls `deleteEntry`. The latter takes the shared queue but performs no version comparison (`user-work/registers.server.ts:45`). Finally, `local-case/user-work.server.ts:390-394` deletes by case, store and row ID only.

This is not an unconfirmed-delete bug or a failure of transaction serialization. The current controls work as written. The omitted condition is whether the saved row still matches what the confirming user saw. The edit path demonstrates the intended optimistic conflict handling (`user-work/registers.server.ts:34-41`, `page.server.ts:110-115`); that does not extend to deletion. A current-view delete remains legitimate, and repeated deletion of an already absent row is harmless.

**Priority correction.** P2 is proportionate for the local single-operator pilot: another tab must save a change while this tab remains stale, followed by an intentional confirmed deletion of the same row. The impact is real lost saved text, but narrower than an ordinary case switch mixing evidence or import conflating case identity. No broad unauthenticated deletion, multi-user hosted race or irrecoverability of all backups is established. The seven generic register views share this path (`defs.ts:3`).

**Proof needed.** Load a row in two browser tabs, save a distinct marker in B, then confirm deletion from A. Check that a repaired implementation refuses the stale mutation and leaves B's complete saved row unchanged. Also edit after A opens confirmation, exercise the non-JavaScript form path and stale/missing versions, and retry after restore. Keep comparison and deletion within the same queue/transaction boundary; an extra client refresh alone leaves another race window. The rejection should return current row state so the user can make a new informed decision.

## SI-01 — multipart completion can replace acknowledged probe bytes

**Scope and actual path.** All references in this section are at incoming **a3f80d1305294a8c685a87351281eef7928c7d9c**. `tests/hosting-probe/storage/src/worker.ts:1-4` explicitly declares a storage probe without identity/session handling. `open` at lines 101-119 checks client bindings, not per-key writer ownership. The bucket proxy only counts operations. Completion at lines 1137-1146 checks absence and then separately invokes `complete`; initiation at lines 1127-1130 has the same non-atomic absence check. Two independent upload IDs can therefore be created before the key exists.

**Counterarguments assessed.** Strong consistency makes each head result meaningful at its observation time; it does not reserve the key. The documented Workers API exposes `complete(uploadedParts)` without a conditional parameter and permits parallel invocations. This supports the race inference, not an assertion that the exact scheduling has been observed. [Cloudflare R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/#r2multipartupload-definition).

Finalization hashes bytes and commits D1 references (`worker.ts:268-298`), but cannot fence a completion which already passed its absence check. The interleaving is: both completions observe absence; A completes; A finalizes and is acknowledged; B completes different bytes into the same key. B need not finalize. A single PUT can be the winning writer too. Conversely, competing successful single PUTs supply the expected SHA-256 at line 260; absent a digest collision, that path alone does not demonstrate different-byte replacement.

The existing write-once test at `probe.ts:853-858` stores and finalizes the winner **before calling** the losing completion. It proves refusal when head sees an existing key, not refusal after two heads saw absence. Later digest/etag-checked reads (`worker.ts:223-247`) mitigate wrong-byte delivery but cannot restore the winning object. The potential blast radius is all references to that digest **within the same client's bucket**, not all clients. The earlier reproduction's acknowledgement marker was not a D1 commit.

**Priority and proof.** Retain P1 as a blocker to claiming the probe establishes safe write-once storage or adopting this design for acknowledged originals. Reject any characterization as a confirmed current hosted-product exploit: baseline production services return `ready:false` (`src/lib/server/runtime/hosted/services.ts:15`), and protected routes refuse before resolution (`handle.ts:34`). Native workerd/local R2 testing must hold both completions after their head checks, execute actual A finalization, release B, and inspect both persisted D1 rows and exact R2 bytes. Include PUT versus multipart and independent upload IDs. Local workerd evidence must not be labelled cloud acceptance.

The proposed unique upload-object key plus atomic D1 publication approach removes competing writes to the winning key, provided all later reads resolve that exact object. This is a storage-contract change, not just another check before `complete`. A coordinator alternative must cover every writer and recovery. A process-local mutex or additional head request is not a reliable fix.

## SI-02 — source hash does not verify a partially written snapshot

**Why it survives challenge.** `fsafe.server.ts:59-69` correctly advances input reads by actual `bytesRead`; it does not validate destination writes. `snapshotVerified` at lines 80-87 hashes the input chunk, awaits one `out.write`, ignores `bytesWritten`, advances by the requested length and checks the input's identity/hash. The [FileHandle API](https://nodejs.org/api/fs.html#filehandlewritebuffer-offset-length-position) reports the number actually written. `sync()` flushes writes; it does not establish that all requested bytes were written.

The consumer is real: `originals.server.ts:183-209` uses this helper above the configured buffer threshold and streams the resulting descriptor without a destination size/hash check. Default threshold is 32 MiB (`config.server.ts:51`). Source containment, original size/hash checks, exclusive temporary-file creation and cleanup do not repair a short destination write. An early partial write followed by later positional writes can leave an internal gap while preserving the expected final length. A final short write may instead appear as an incomplete HTTP response; not every fault yields silently accepted corruption.

**Limits and priority.** Retain P2 as an I/O-integrity repair. The earlier fake file handle demonstrates the algorithm under the short-write contract, not that Bun 1.4.2 on supported Linux returns this result under a measured real fault. No attacker-controlled filesystem failure or original-file modification is established. Ordinary thrown write/sync errors already cause refusal and cleanup; the finding concerns a successful short return which escapes that branch. “Verified” means the helper's boolean, not a formal runtime certification.

**Proof needed.** Test early and final short writes, repeated short progress, zero progress and thrown errors through the actual helper. Then run the supported large-original HTTP path with synthetic data, checking full response bytes and temporary-file cleanup. The required outcomes are exact bytes or refusal; file length alone is insufficient. Looping on actual bytes written with zero-progress refusal addresses the demonstrated gap without changing source originals.

## SI-03 — generated PDF retains page additional actions

**Why it survives challenge.** `assemble.ts:402-405` copies the page dictionary after removing a specific key list that includes `Annots` and `Parent` but not `AA`. `writer.ts:130-156` recursively copies dictionaries, indirect objects and streams; it does not interpret or strip action dictionaries. Later assembly updates contents/resources/parent without removing `AA`. Thus a valid page `/AA` opening action can remain connected to the generated page, including indirect JavaScript content.

The builder invokes this assembler and offers its bytes through blob download/open/preview (`Builder.svelte:79-84,193-196`). It does not send the generated PDF through the isolated originals viewer. The rebuilt catalog and removed source annotations do eliminate other entry points; it would be incorrect to infer that every original document-level script, attachment or annotation is preserved. Conversely, those controls do not remove this page-level action.

**Limits and priority.** Retain P2 for unexpected active content in a generated derivative. Adobe documents scripts triggered by opening a page, but execution remains reader/settings dependent. [Acrobat JavaScript contexts](https://developer.adobe.com/acrobat-pdfl-sdk/guides/jsdevguide/js-dev-contexts). This is not demonstrated Chromium execution, app-origin XSS, exfiltration, OS code execution or sandbox escape. The prior `void(0)` diagnostic demonstrates retained structure only. No explicit promise that the assembler is a comprehensive PDF sanitizer was established; the actionable requirement is an explicit derivative active-content policy, not an invented claim that all PDFs are safe.

**Proof needed.** Generate output from inert synthetic direct and indirect `/AA` actions, including action chains; inspect the generated object graph with an independent reader/parser and confirm the forbidden actions are absent after repair. Keep visual page content, numbering and generated index links intact. Any stronger claim about executable consequences requires a benign action in a named reader/version with recorded security settings. Removing page `AA` closes this demonstrated entry point; calling the entire derivative sanitized requires a broader allowed-object/action policy and separate evidence. Original PDFs must remain byte-exact.
