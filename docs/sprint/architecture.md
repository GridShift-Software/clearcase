# Cloudflare-only target architecture for ClearCase (Fable 5.1, read-only, dev 1ed4b634, 28 Oct 2026)

Read: both why-slow reports, the spin-down handoff, the five bulk-processing notes, ADRs 0007-0011 and 0013 (branch `rx27/adr-0013-paid`), `docs/processing-contract.md` (same branch; neither is on dev), `docs/results-package.md`, and the named source files. Cloudflare facts were re-read today on developers.cloudflare.com (Firecrawl CLI is not installed; WebFetch used). Nothing was run, deployed or called.

**Verdict: Cloudflare alone works.** The one thing it genuinely cannot do is keep data at rest in South Africa: D1 and R2 have no African region or hint (D1 says "do not run in" Africa; R2 hints are wnam/enam/weur/eeur/apac/oc; jurisdictions eu/us/fedramp) [1][2]. Workers do run in Johannesburg, Cape Town and Durban [3]. Smallest workaround: pin every Worker to London (`[placement] region = "aws:eu-west-2"`) beside `eu`-jurisdiction D1 and R2, so a request pays one JNB-to-London hop (about 160 ms) instead of one per database call, and serve the immutable read model from the JNB edge cache so most page views never cross that hop. Today's slowness is call count, not Cloudflare: 86 D1 and 16 Clerk calls per published page, 46 D1 per uploaded file, and three whole-object reads plus three SHA-256s per PDF open (why-slow-claude.md; `delivery.ts`, `objects.ts`).

## 1. Request-path budget (targets per request, then how)

| Path | Clerk | D1 | R2 | How |
| --- | --- | --- | --- | --- |
| Page view (overview, chronology page, files page) | 0 | 1 | 0-1 | grant row + shard pointer in one query; shard from Cache API, R2 on miss |
| PDF open, first byte | 0 | 1 | 1 | one `get` with `range` and `onlyIf: {etagMatches}`, streamed, no hash |
| PDF range request (pdf.js, dozens per doc) | 0 | 0 | 1 | signed asset ticket, see below |
| Mutation (note, sign-off) | 0 | 1 batch | 0 | change + audit row in one `db.batch` |

- **Authorize once, verify locally.** Clerk's `authenticateRequest({ jwtKey })` verifies the session JWT against the instance's JWKS with no network call [4]. Remove `sessionStands` from `authenticate` and from every `authorize` (`provider.ts:97-140`); keep JWKS in KV, refreshed hourly. Revocation: sign-out writes `revoked:<sid>` to KV (TTL = session max age); the request checks that one KV key (edge-cached, ms). Revocation lag is KV's propagation, about a minute, instead of zero. Grants: one indexed query `grants WHERE subject AND case_id` per request; drop the second grant read and the `cases.exists` round trip (`authorizer.ts:62-66`).
- **Audit without read-back.** `d1-log.ts` INSERTs, then SELECTs the row back, then reads counters (3 sequential calls). Mutations: audit row in the same batch as the change, so it commits or neither does. Reads: one audit row appended in `ctx.waitUntil` (`waitUntil` has 30 s after the response [5]). Fail-closed on audit stays only for mutations.
- **Originals.** Hash at ingest, never on read. R2 `put` takes a `sha256` option and refuses a mismatch; `head()` returns `checksums.sha256` and `httpEtag`; `get()` takes `range` and `onlyIf` [6]. Store size, sha256, etag and the sniffed media family in the catalogue row at ingest, so `delivery.ts` loses its 1 KiB probe read and its second full read. Integrity on read is etag match against the recorded etag. The viewer page mints an **asset ticket**: HMAC over (user, asset key, expiry 15 min); pdf.js range requests present it, so they cost 0 D1 and one Class B op each. Downloads over about 100 MB and zip exports redirect to a **presigned S3 GET** (GET/HEAD/PUT/DELETE, up to 7 days, S3 endpoint only, not a custom domain; CORS on the bucket) [7]. Keep PDFs same-origin through the Worker so the sandbox CSP in `delivery.ts` still applies.
- **Sessions that survive long tasks.** The 60 s Clerk token with no clerk-js is the premise behind five renewal rounds. Replace it: after Clerk sign-in, the Worker sets an HttpOnly app session cookie (HMAC, sid, 8 h sliding, max 24 h) and checks it plus the KV revocation key on every request. Clerk is consulted only at sign-in and sign-out. Long uploads and imports no longer touch sessions at all (section 3).
- **Immutable per-version read model.** At import the operator machine writes, per version, JSON shards to R2: `rm/<case>/<version>/overview.json`, `chronology/<page>.json` (200 rows), `files/<page>.json`, `doc/<ref>.json`, each with `Cache-Control: public, max-age=31536000, immutable`. The Worker authorizes, then `caches.default.match`, `put` on miss. Cache API is per data centre [8], so the first viewer in JNB warms it for everyone there; KV holds `published:<case>` -> version id (25 MiB values, 1 write/s per key) [9]. Publication flips the KV pointer; the whole `loadVerifiedModel` (every row of `rs_document`, `rs_asset`, `rs_seed` per request, `model.ts:16-25`) goes away. Cache Reserve is not needed and does not cover Worker-generated responses anyway [10].

## 2. Storage for 1M+ files

- **R2** (`eu` jurisdiction, `weur` hint, one bucket per client): originals content-addressed `orig/<sha256[0:2]>/<sha256>`; converted previews `prev/<sha256>.pdf`; compressed text `text/<sha256>.zst`; read-model shards; bundles and exports. Limits are not a problem: unlimited objects, 5 TiB per object, 10,000 parts, key 1,024 B [11]. Store the long tail in Infrequent Access only after measuring reads (IA retrieval $0.01/GB, 30-day minimum).
- **D1** (10 GB per database, 50,000 per account, 1 TB per account, 1,000 queries per invocation, 2 MB per row, 5 GB `d1 execute` import) [12]. The client database keeps users, grants, cases, audit, versions, jobs and a `shards` registry. **One catalogue database per case** from day one: a row per kept file (path, name tokens, custodian, size, sha256, etag, media family, batch id, parent for attachments) is about 300 B plus indexes, so a database holds roughly 8-10 M rows. A 15 TB case deduplicated is estimated at 5-10 M items (plan.md), so sharding by custodian or top-level folder is needed only past about 6 M rows; design the `shards` table now, split later. Per-document published results (3-4 KB each today) do not go in D1 at this scale; the row keeps a 200 B index entry and a shard pointer. Each D1 binding is static in `wrangler.toml`, so a new case database means a redeploy; if that bites, Durable Objects SQLite is the alternative (same 10 GB per object, unlimited objects, $0.20/GB-month, same rows-read rates [13]).
- **KV**: JWKS, revocations, published pointers, grant cache (60 s TTL) if the single grant query ever shows in traces.
- **Search.** File names first: D1 FTS5 is supported [14]; index `name || path || custodian` tokenised on `_ . - space`, query per shard and merge, keyset-paged. About 150 MB per million names. Full text later: a BM25 index over 200 GB of case text does not fit D1, Vectorize or KV. Cloudflare-native options: AI Search (1 M files per instance, 10 MiB per file) for the published set; a **Container** (4 vCPU, 12 GiB, 20 GB ephemeral disk, scale to zero) running tantivy or quickwit with splits on R2 for the full corpus. Embeddings: Vectorize holds 20 M vectors per index at up to 1,536 float32 dims [15], so one vector per document per case fits; page-level vectors only for the processed subset.
- **Paging.** Keyset on (sort key, rowid), 100-200 rows per page, 2-3 queries per screen, counts from a summary table maintained by the importer, never `COUNT(*)` over millions. Chronology and records views page the same way; the "render every row then `includes`" display check is removed, not fixed.

## 3. Ingest

- **Originals bypass Workers.** From the NAS or the operator machine, `rclone copy` to the client bucket over the S3 API with a bucket-scoped object read/write token: `--transfers 32 --checkers 32 --s3-chunk-size 64M --s3-upload-cutoff 200M --s3-no-check-bucket`, keys from the manifest the funnel already produced (sha256 as key, so a retry is idempotent and dedupe is free). Verify with `rclone check` against the manifest, then `HEAD` sampling. R2's S3 API supports Content-MD5 and conditional GET/Range [16]. Class A cost: 10 M objects about $45 once, plus one op per multipart part.
- **Time at 80% line efficiency:** 1 TB takes 28 h at 100 Mbps and 2.8 h at 1 Gbps; 15 TB takes 17.4 days at 100 Mbps and 1.7 days at 1 Gbps. Over 100 Mbps the upload is the schedule, so order it published-likely first and get a symmetric gigabit line for the upload fortnight.
- **Results are one sealed bundle per batch.** The operator machine runs the existing validator (`results-package.md`) offline, then writes a `bundle.json` manifest: batch id, case, parent batch, every part's path, size and sha256, counts, and the attested receipts (render checks, page counts, META reconciliation) that `evidence-gate.ts` and Browser Rendering compute online today. Parts: catalogue rows as NDJSON shards (at most 64 MiB each), read-model shards, text shards. rclone uploads the parts; one Worker call `POST /operator/cases/:id/batches {manifestSha256}` starts a **Workflow**: one step per part streams and hashes it (unlimited wall time per step, 10,000 steps, 1 GB state [17]), one step per 2,000-row D1 batch (one query each against the 1,000 limit), then a candidate version row. Sign-off binds the manifest root digest exactly as ADR-0010 and `d1-publisher.ts` do today; publication is the KV pointer flip. This replaces the results-package bounds (1,024 files, 512 MiB, 32 GiB) with a manifest of parts and the staged-import leases.
- **Incremental batches.** Catalogue rows are append-only with `batch_id`; a published version is a list of batch ids plus the processed-results shards for that version. Clients read batch N while N+1 sits in preview; refs stay stable per the processing contract. Reprocessing a batch produces a new version, never an edit.

## 4. Environments and promotion

- One Cloudflare account, one codebase. Wrangler environments deploy separate Workers named `<name>-<env>`, with bindings, vars, secrets and routes set per environment [18]: `clearcase-client-a`, `clearcase-client-b`, `clearcase-staging`, and `clearcase-load` for stress tests (its own D1, R2, KV, Clerk development instance, synthetic data only). Custom domains need the `clearcase.co.za` zone active (nameservers still pending, `custom-domain.md`): `[[routes]] pattern = "client-a.clearcase.co.za", custom_domain = true`; no wildcards, one hostname per environment [19].
- **Placement in config, not the dashboard:** `[placement] region = "aws:eu-west-2"` (or `gcp:europe-west2`) in every environment [20], the same region as the D1 and R2 hint, so a deploy cannot drop it. Check `cf-placement: remote-LHR` on the live header.
- **Promotion:** CI builds once per SHA -> `wrangler versions upload --env staging` -> `versions deploy` -> Astra journeys plus a k6 run from a Johannesburg fleet host against `clearcase-load` -> tag -> `versions upload --env client-a` -> `versions deploy` at 10%, then 100%; `wrangler rollback` if the error rate moves [21]. Migrations: `wrangler d1 migrations apply --env <env>` before the version deploy; additive only while two versions overlap.

## 6. Delete or bypass, and keep

**Delete or replace:** `objects.ts` `verifiedRead` (whole read plus hash) -> range `get` with etag condition. `viewer/hosted/delivery.ts` probe and second read -> one read, family from the catalogue row. `results/hosted/model.ts` `loadVerifiedModel` and `reader.ts` `collect`, `listJson`, `originalAttributions` -> R2 shards and indexed lookups. `auth/clerk/provider.ts` `sessionStands` on every call and `browser.ts`'s no-renewal premise -> networkless verify, app session cookie, KV revocation. `tenancy/authorizer.ts` double grant read, `exists` call and audit-before-allow -> one query. `audit/d1-log.ts` read-back and counters. `storage/cloud/intake.ts` finalize re-read and re-hash. **Bypass entirely** (work moves to the operator machine and the bundle): `results-review/native/*` and `server/runtime/hosted/stepped-stager.ts`, `candidate-stager.ts`, `evidence-gate.ts`, `required-section-render.ts`, `publication-material.ts`, `viewer/hosted/native-render-check.ts`, `publication/hosted/originals-evidence.ts`, `readiness-evidence.ts`, the Browser Rendering binding and daily render quotas, the 2,000-original publish cap in `d1-publisher.ts`, and the `warning_fingerprints` and `coverage_json` single-row blobs.
**Keep:** the grants model and roles in `tenancy/` (per-case, explicit, revocable, upload grants), Clerk sign-in and operator routes, the audit schema and public reader, exact-version sign-off and the ledger in `publication/hosted/` (rebound to the manifest root), the package validator in `case-package/` (run offline), `submissions/` for small ad hoc client uploads (bulk never goes through it), and `deploy/native-alpha` provisioning.

## 7. Migration steps (engineer-days; P = parallel, S = sequential; two engineers, about 2.5 weeks)

1. **F, P, 1 d, start now:** rclone runbook, bucket-scoped tokens, manifest check, pilot 100 GB upload to the staging bucket; measure the office line.
2. **A, S, 2 d:** networkless Clerk verification, app session cookie, KV revocation, one grant query, audit in batch and `waitUntil`. Opus or Sol security review once.
3. **B, P with A, 1.5 d:** range streaming with etag check, asset ticket, presigned downloads, ingest-time hash and family columns.
4. **G, P, 2 d:** staging and load environments, placement in config, custom domains once the zone is active, versions-based promotion in CI.
5. **D, P with A, 4 d:** catalogue schema per case, `shards` registry, Files screen with FTS5 name search and keyset paging, synthetic 1 M-row fixture, latency measured from Johannesburg.
6. **C, S after A, 3 d:** read-model shards, KV published pointer, Cache API serving, chronology and records paging over shards.
7. **E, S after D, 4 d:** bundle manifest, Workflow importer, attested receipts, sign-off on the root digest, incremental batches, removal of the staged import and online evidence.
8. **H, S after C and E, 2 d:** CI round-trip budget test (at most 3 D1, 0 Clerk, 1 R2 per route), k6 from Johannesburg, Astra journeys at the deployed SHA; make p95 under 1 s for page views and 2 s to first PDF page a release gate.
9. **Phase 2, later, 5 d or more:** full-text search container or AI Search, Vectorize embeddings, bundle and export jobs on Workflows.

Critical path A -> C -> E -> H is about 11 days; D, B, F and G fill the second engineer. Not verified: live latencies, Clerk's current session-lifetime defaults (page 404 today), S3 `x-amz-checksum-sha256` header support on R2 (the page lists Content-MD5 only), and D1 FTS5 trigram support.
