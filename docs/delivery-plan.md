## Delivery controls

Accepted under [GRS-94](https://linear.app/vaper/issue/GRS-94/define-the-fable-and-swarm-delivery-operating-plan). The [operating plan](plan/agent-delivery-operating-plan.md) and the [hosted-alpha acceptance baseline](plan/hosted-alpha-acceptance.md) hold the full text. These controls replace the 8 October brief boilerplate kept in historical tickets.

- **Roles.** First implementation runs on `claude-opus-5-5` at effort xhigh, independent diff reviews at xhigh and the recheck of a fix diff at high. Fixes from written findings, merges, and PR and Linear text run on `claude-sonnet-5-5` at high. A high finding that survives the fix round gets one Opus xhigh round with `diagnosing-bugs`. No agent runs at effort `max`. Deterministic checks run as scripts that leave receipts, not as model calls.
- **Rare escalation.** Only a documented blocker that survives the normal loop escalates, to one of `claude-fable-5-1` at effort xhigh or `gpt-6-astra` at reasoningEffort xhigh, never both. Before dispatch, create the linked Linear escalation issue with the source issue, exact SHA, reproduction, prior attempts, bounded question, model, spend target and completion predicate. Afterwards, record the T3 task ID, findings, outcome, SHA and checks on it.
- **Attempts.** One written-finding fix round with a fresh recheck, at most one justified rare escalation and one transient infrastructure retry. Stop when the same failure repeats twice without a new diagnosis. Attempts count against the original issue and stage, so renaming, restarting or redispatching a task does not reset them.
- **Runtime.** Writing tasks get 90 minutes and reviews 30 minutes. Assess a stall after 30 minutes without meaningful progress. Declare bounded long tests and per-task deadlines in the brief, give a short checkpoint grace, cancel explicitly and keep the branch, evidence and cancellation result. A T3 wait timeout is not a runtime limit.
- **Spend.** The targets are build 20, review 6, written fix 8, recheck 2 and escalation 12 USD. Report actual or unknown spend and the variance. Overspend alone does not pause, cancel or escalate work.
- **Capacity.** At most three worker jobs and two browser jobs. PC2 is the first isolated synthetic test pool and PC1 keeps its CI role.
- **Checks.** Scale checks to the change. App changes keep the required gate until its hosted replacement is reviewed, and documentation or research gets proportionate checks. Mutation and perf runs are for milestone gates only. A skipped, mocked, weakened or other-revision check is not a pass.
- **Merge.** One branch and worktree per writing ticket, cut from the wave branch `wave/<name>` its brief names (or from the upstream ticket's branch while that is unmerged). A ticket PR targets its wave branch and a wave PR targets `dev`; nothing else targets `dev`. Merge commits only and serial integration on accepted upstream heads. The external reviewer `dianbrown` reviews the wave PR, and nothing merges into `dev` before that approval. `main` changes only through the user.
- **Gate.** GRS-69 is Done: the user approved the complete written plan on 17 October 2026 (GRS-69 comment `45db4bdd-c268-4f6b-8658-cc2edb77bc6a`). Hosted work follows the native blockers, and every hosted runtime, provider and acceptance check is UNRUN until its own ticket proves it. The hosted gate (GRS-138) is the required check for hosted tickets once it lands.
- **Waves and checkpoints.** A wave is the set of tickets under one checkpoint aggregate (GRS-27, GRS-36, GRS-137, GRS-66, GRS-32), at most seven tickets, on one branch. At a checkpoint the user reads the aggregate report and drives the verification skill once. Agents run unattended between checkpoints. See [verification and review](plan/verification-and-review.md).
- **Human gate.** Running the manual processing recipe over case documents is the user's own step in a separate chat. A worker stops with `AWAITING MANUAL RESULTS`, names the submission manifest and the download path, and resumes from the import step once the user supplies the package.
