## Strengths worth preserving

- **Failure is visible before access.** Production refuses missing services, the build distinguishes production from hosted-gate, and source/artifact guards exclude local modules and doubles. I:`vite.config.ts:6–24,52–54`; `docs/development.md:74–94,124–139`. Current Svelte documentation supports the selected adapter, `cloudflare:workers` bindings and `nodejs_als`; the narrower flag is deliberate, not a defect to “fix” by blindly enabling all Node compatibility. [Svelte adapter](https://svelte.dev/docs/kit/adapter-cloudflare), [Workers Node compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/).
- **The deployment proof checks actual targets.** N:`deploy/probes/target.ts:69–97,136–150,217–251` validates data-only configs, client identifiers, staged artifacts and prebuilt outputs. Dry runs alone can miss a swapped database. Keep this boundary when extending provisioning; use in-process bindings rather than account API credentials in the application. [Workers bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/).
- **Storage distinguishes publication from durable user work.** N:`docs/acceptance/hosting/storage.md:119–178` uses R2 for immutable bytes, D1 for indexed records and revision-guarded batches; publication is an active-version pointer. Snapshot rows and revision now share one batch. D1 documents batch transaction rollback, supporting that design; it does not make R2 and D1 one transaction. [D1 batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).
- **Recovery is more than a ZIP download.** N:`docs/acceptance/hosting/recovery.md:37–43,69–76` separates recovery copies, deletion records, live data and bundle retention, and resumes interrupted erasure. The reports explicitly distinguish a recovery backup (including Notes) from the Complete case export (Notes opt-in). Preserve that distinction from I:`docs/adr/0011-originals-and-complete-in-app-file-viewing.md` and GRS-118.

## Prioritized findings

P1 means a release blocker or a correctness condition that must be resolved before the relevant hosted path is accepted. P2 means a bounded improvement or explicit supported-envelope decision before rollout. None alleges an observed production incident.

### CF-01 — P1: production adapters and live boundary evidence are absent

**Trigger/impact.** Deploying the integrated production artifact produces 503 for protected routes; deploying the gate profile would expose a test design. Incoming standalone probes do not change this. I:`src/lib/server/runtime/hosted/services.ts:8–15`; `deploy/client/routes/sign-in/+page.server.ts:10`; `docs/development.md:76–94`. N:`docs/acceptance/hosting/deployment.md:159–165`, `storage.md:211–222`, `identity.md:3–5` and its summary HOLD array establish the outstanding provider legs.

**Smallest next step.** Finish the existing adapter/provisioning owners, then exercise M1/M2/M3 only under the account owner's authorization. Preserve the fail-closed production profile. GRS-137 must use the actual manual recipe and candidate import, sign-off and publication, followed by GRS-32 at the exact release SHA. A local POC is a development tool; Cloudflare documents local development as emulation of production bindings, not a substitute for remote behavior. [Local development](https://developers.cloudflare.com/workers/development-testing/).

**Validation.** Signed-in client A can complete the agreed hosted flow; client B and revoked grants cannot reach the same bytes. Record source SHA, deployed Worker version, target manifest digest, fixture, provider/environment and actual outcomes. Include originals/ranges, recovery, exports and the result-import boundary. **Confidence: high.**

### CF-02 — P1 handoff: the trusted target schema cannot yet express the recovery/EU design

**Trigger/impact.** N:`deploy/probes/target.ts:41–42,78–88,140–145,219–222` accepts one D1 and exactly one R2 bucket, and disallows an R2 `jurisdiction` field. N:`docs/acceptance/hosting/recovery.md:37` requires a separate per-client `RECOVERY` bucket. N:`storage.md:213–221` requires EU placement. A faithful production config is therefore rejected by this probe schema. Omitting those fields to get through the checker would silently abandon the intended deployment.

**Smallest fix.** GRS-114 extends the existing reviewed manifest/check/stage/prebuilt path for the selected live and recovery buckets, jurisdictions, actual secret names, client/staff issuer/origin configuration and any selected operational settings. Keep exact allowlists and negative validation. This is an expected integration gap in a bounded probe, not a reason to loosen the checker globally. D1 jurisdiction is chosen when creating the database; R2 jurisdiction must also appear in its Worker binding and jurisdiction-specific S3 endpoint. Location hints alone are not guarantees. [D1 location](https://developers.cloudflare.com/d1/configuration/data-location/), [R2 location](https://developers.cloudflare.com/r2/reference/data-location/).

**Validation.** Correct client A config stages; swapping either bucket, database, issuer/origin or jurisdiction is refused. Remote resource inspection verifies the manifest before any synthetic case upload. Keep static assets in the tested deployment path: N:`deployment.md:169` says the cf prebuilt path has not yet pinned its assets directory. Use the measured Wrangler fallback if the preferred tool cannot carry the complete artifact. **Confidence: high.**

### CF-03 — P1 proof gap: acknowledgement is not yet tied to recoverability

**Trigger/impact.** The storage probe acknowledges an original after live R2 verification and a D1 batch (N:`tests/hosting-probe/storage/src/worker.ts:268–298`). Recovery copies are created separately from an already-sealed export (`tests/hosting-probe/recovery/src/worker.ts:416–429`). The recovery drill restores copies made before later edits; it does not show an acknowledged upload surviving loss of the live bucket before its next copy. N:`recovery.md:71–74,108–109,132`. This leaves the accepted “acknowledged uploads remain recoverable” objective unproven; Time Travel cannot recreate R2 bytes.

**Smallest fix.** GRS-117/118 specify the acknowledgement-to-recovery invariant and implement it using the selected stores: either recovery protection precedes acknowledgement or the declared failure model and copy mechanism demonstrably preserve every acknowledged original. Define and observe copy freshness; do not infer it from a 30-day retention window. Include durable bundle outputs or document an accepted regeneration/recovery decision with GRS-128. Coordinate grants, withdrawal and audit recovery with their existing owners. [D1 Time Travel scope](https://developers.cloudflare.com/d1/reference/time-travel/), [R2 durability](https://developers.cloudflare.com/r2/reference/durability/).

**Validation.** A synthetic upload is acknowledged, the live-store failure is injected immediately, and its exact bytes recover. Write timed Notes/case edits around real Time Travel restore/undo; identify lost writes and verify the one-hour objective. Reapply deletion, withdrawal and revoked-access rules before serving. Measure staffed restore duration, but keep the four-hour aim a soft goal, as GRS-93 requires. **Confidence: high for the proof gap; the final failure model remains an owner decision.**

### CF-04 — P1: migration rollback needs a code/data compatibility drill

**Trigger/impact.** N:`docs/acceptance/hosting/deployment.md:83–84,114–116,163` records local migration tests and source inspection of Void's automatic remote migration/bookmark behavior; remote execution and Worker rollback remain HOLD. Returning to an earlier Worker does not undo its D1 schema/data changes or restore R2 objects. Time Travel overwrites the entire database and cancels in-flight queries. In the one-database layout it can also undo unrelated user edits. [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/), [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/).

**Smallest fix.** GRS-107/114 record a deployment tuple: app SHA/artifact digest, config digest, Worker version, migration set and pre-migration bookmark. Prefer additive migrations compatible with the previous app; record when fix-forward or write quiescence is necessary. Keep publication rollback, Worker rollback and disaster recovery as distinct runbook actions. Do not make whole-database restore the default code rollback. [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/).

**Validation.** On a disposable authorized cloud target, run a successful migration, an intentionally failing one, old code against the resulting schema, Worker rollback, and database restore/undo where required. Prove which writes survive each step. For one or two clients, follow the accepted one-client-first operational rollout; traffic-percentage deployment is optional later because simultaneous versions introduce version skew. [Gradual deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/). **Confidence: high.**

### CF-05 — P1 before adopting storage code: close R2 write races and deletion/write races

**Trigger/impact.** N:`tests/hosting-probe/storage/src/worker.ts:375–386` performs HEAD then unconditional PUT for a staging package key. Two different payloads can race, leaving bytes inconsistent with D1; verification refuses them, but service availability is lost. Its multipart completion also checks HEAD then completes (`1127–1145`), without a conditional completion. Unlike single PUT, multipart bytes have not yet been checked against the claimed digest (`278–282`). Two in-flight uploads therefore need an explicit concurrency proof; a shared hash-shaped key alone does not establish identical bytes. N:`storage.md:162` already records non-atomic writes. Separately, N:`recovery.md:188–192` records a write that passes its deletion check and commits after erasure, and a shared-original deletion race.

**Smallest fix.** GRS-115/117 adopt conditional creation for applicable PUTs, handle its failed-precondition result, and keep the deletion predicate inside each D1 write batch. For multipart, choose a recoverable ownership protocol or upload-specific staging keys with a guarded verified-object association; do not invent a conditional option on `R2MultipartUpload.complete`, whose documented API accepts only parts. Keep reconciliation for cross-store failures. [R2 consistency and concurrent writes](https://developers.cloudflare.com/r2/reference/consistency/), [R2 conditional operations/API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

**Validation.** Force two writers past HEAD before either completes, including different multipart bytes claiming one digest; assert an acknowledged original cannot be replaced. Race removal against Notes save, upload finalization and restore; no new live row or orphaned case object may survive the completed protocol. The multipart scenario is a static risk inference, **not a reproduced failure** here. **Confidence: high for documented HEAD/PUT and deletion races; medium for the exact multipart interleaving pending a deterministic test.**

### CF-06 — P2, cheap fix: JSON batching measures UTF-16 characters instead of bytes

**Trigger/impact.** N:`tests/hosting-probe/storage/src/worker.ts:312–332` uses `JSON.stringify(r).length` against 900,000 while naming the counter `bytes`. Non-ASCII input can exceed remote D1's bound-value ceiling despite passing the ASCII-heavy local corpus; the code also needs an individual-row limit. N:`storage.md:231` acknowledges the residual. D1's limit is bytes, and local acceptance is not proof of remote enforcement. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

**Smallest fix.** GRS-115/117 count UTF-8 bytes of the exact serialized array, including separators; reject an oversized individual row with an actionable import error. Retain the lower chunk budget rather than filling the provider maximum.

**Validation.** ASCII, non-Latin text, combining characters and emoji near the bound; one oversized row; the same cases on disposable remote D1. Confirm atomic refusal leaves no published partial version. Measure query count/rows before and after. **Confidence: high.**

### CF-07 — P1 measurement; P2 tuning: prove streaming and range costs under actual concurrency

**Trigger/impact.** A 64 KiB range of the largest synthetic original causes a whole 258,590,305-byte verification read; a delivery beyond 32 MiB performs two reads. N:`storage.md:111–115,204–209`; `tests/hosting-probe/storage/src/worker.ts:39–43,145`. The local 2,350 ms range timing is not a hosted latency budget. Four simultaneous maximum-size 32 MiB buffers already consume 128 MiB before other allocations. The large two-pass stream can send earlier bytes before its second digest fails; the report correctly discloses that limitation (`storage.md:113,228`).

**Smallest next step.** Run existing M2 P1/P3/P5 with concurrent actual viewer requests, measuring first-byte/completion time, CPU, isolate memory, R2 bytes/operations and retries. Set explicit bounded upload/read/export concurrency and CPU/size limits from those results. Keep hash verification unchanged until GRS-27 resolves its integrity policy. Preserve Range/HEAD/If-Range behavior, content lengths and aborted-stream detection in clients. Streaming is necessary but does not eliminate hashing CPU or shared-isolate memory. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/).

**Validation.** Largest original, many small PDF ranges, cancelled/repeated ranges, damaged bytes outside the requested range, and concurrent export/restore. Note that `RESTORE_STEP_BYTES = 64 MiB` is a threshold between entries, not a hard maximum: `restoreStep` adds an entire next entry (`worker.ts:907–925`), so one 258 MB entry can exceed it. Measure the actual worst invocation. N:`recovery.md:194` also documents single-PUT copy/staging failure above 5 GiB. GRS-118 must either enforce a measured supported backup envelope before acceptance or implement resumable multipart copy; silently discovering the ceiling during recovery is unacceptable. [R2 limits](https://developers.cloudflare.com/r2/platform/limits/), [multipart API](https://developers.cloudflare.com/r2/api/workers/workers-multipart-usage/). **Confidence: high for code paths; actual cloud capacity unmeasured.**

### CF-08 — P1 operational proof: rotation timing does not yet establish the accepted deletion bound

**Trigger/impact.** N:`tests/hosting-probe/recovery/src/worker.ts:464–482` deletes objects older than 30 days at a caller-supplied test time. The handoff proposes a daily scheduled sweep (`recovery.md:167,176`), which can retain an object almost another day past its 30-day birthday. R2 lifecycle deletion is typically within 24 hours after expiration and can be delayed; a rule set to 30 days is not an exact 30-day physical-erasure guarantee. [R2 lifecycle timing](https://developers.cloudflare.com/r2/buckets/object-lifecycles/).

**Smallest fix.** GRS-118 and the GRS-93 policy owner reconcile the documented “within 30 days” requirement with actual scheduling/provider timing: choose an earlier expiration target with operational margin, measure overdue objects, and document the accepted guarantee. Preserve live cases, protected bundle history and permanent deletion records. Production uses the platform scheduled timestamp, never the probe's HTTP clock. Do not claim a hard physical-deletion deadline from eventual lifecycle cleanup alone.

**Validation.** Expiration just after a sweep, a missed/failed sweep, pagination, interrupted deletion, and a real lifecycle/cron run. Check both live scratch and recovery stores, plus all `restore_object` leftovers. Demonstrate the operator can see and resolve overdue cleanup. **Confidence: high; this is a policy/implementation mismatch to settle, not a new retention policy.**

### CF-09 — P2 before go-live: make operational evidence explicit and privacy-bounded

**Trigger/impact.** I:`deploy/client/wrangler.toml` contains no explicit observability policy; `handle.ts:45` logs the raw unexpected error. N:`docs/acceptance/hosting/notifications.md`, “Residuals for GRS-137”, records swallowed D1 failures visible only as log lines and potential outbox starvation. Without deliberately configured telemetry and an operator check, a successful publication can coexist with failed notifications, stale recovery copies or unfinished erasure unnoticed. This does not imply logging is currently disabled remotely—there is no remote config to inspect.

**Smallest fix.** GRS-114 plus existing operations/notification/recovery owners select native Workers metrics/log settings, sanitized structured events and a runbook owned by the Global Admin. Record version, operation kind, duration, result code, attempt count, recovery age and cleanup backlog; keep case text, filenames, tokens, request bodies and sensitive URL parameters out. Review automatic invocation logs, which include request URL metadata. Logs are short-lived operational diagnostics, not the durable permission-scoped audit store. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/), [metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/).

**Validation.** Inject a sanitized synthetic storage failure, expired recovery copy, stuck erasure and failed notification; the assigned operator can find them and follow the runbook. Verify no canary case text/credential reaches retained logs. Prove one chosen alert/escalation path; tune numerical thresholds later as GRS-93 permits. Native Workers Issues is an optional existing-platform route, currently open beta, not a release dependency or authorization to send external alerts. [Issues](https://developers.cloudflare.com/workers/observability/issues/), [alert destinations and privacy](https://developers.cloudflare.com/workers/observability/issues/automations/). **Confidence: high for the missing integrated policy; alert design remains planned.**

### CF-10 — P1 integration proof; P2 measurement: Clerk live revocation is on every protected request

**Trigger/impact.** N:`tests/hosting-probe/identity/src/lib/server/identity.js:83–105` verifies the token then calls `sessions.getSession` for each protected request. This enforces next-request revocation but adds provider latency and a rate-limited dependency to every range/read. Staff sessions share their separate application's limit across client instances. Current Clerk limits are 100 Backend API requests/10 seconds for development and 1,000/10 seconds for production, per application instance; 429 responses expose `Retry-After`. [Clerk rate limits](https://clerk.com/docs/guides/how-clerk-works/system-limits).

**Smallest next step.** GRS-113 measures calls per user journey and simultaneous viewers, and handles rate limits/outage as explicit unavailable states. Do not remove the live check or cache authorization across requests just to improve benchmarks: that changes revocation behavior. Deduplicate repeated authentication within a single request if integration adds duplicate calls. Preserve issuer, session-token type and `authorizedParties` checks. [Clerk request verification](https://clerk.com/docs/reference/backend/authenticate-request).

**Validation.** Actual second-client issuer, production sibling-domain cookie scope, expired-session handshake, revoked session, provider timeout/429 and the real browser's CSP. I:`vite.config.ts:30–46` permits self-hosted scripts/connects and no external Clerk frame; the current probe serves no Clerk JS, so its result does not prove the final UI can sign in under that policy. Add only origins required by the selected Clerk flow; do not paste Next.js-specific unsafe CSP examples into Svelte. [Clerk production setup](https://clerk.com/docs/guides/development/deployment/production), [Clerk CSP](https://clerk.com/docs/guides/secure/best-practices/csp-headers). **Confidence: high.**

## Private caching, retries and deferred optimization

**Keep the current no-store boundary.** I:`src/lib/server/runtime/hosted/handle.ts:7–15,35–36`; N:`tests/hosting-probe/storage/src/worker.ts:122` (the `NO_STORE` helper) and `docs/acceptance/hosting/identity.md:48–49` already avoid caching private responses. GRS-115/118 should verify it on successful ranges, HEAD, errors, redirects, exports and original delivery, then request the same URL after revocation/withdrawal/deletion. The current Workers Cache product can serve before Worker execution; its default key does not include hostname, and cookie authentication alone must not be assumed to bypass caching. Do not enable it for protected routes. Keep public hashed application assets separate from case bytes. [Workers Cache](https://developers.cloudflare.com/workers/cache/), [explicit cache policy](https://developers.cloudflare.com/workers/cache/configuration/). R2's consistency guarantee does not invalidate independently cached responses. [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).

**Retry only operations with a safe repeat contract.** N:`storage.md:24,170–176,230` distinguishes operation IDs, expected revisions and a local dev-proxy retry workaround. Do not transfer the runner's response-text heuristic into production. GRS-115/117 should use bounded retry/backoff with jitter for classified transient D1 failures and preserve operation IDs when acknowledgement is lost. A conflict, stale revision or failed authorization is not a transient retry. D1 already retries retryable read-only queries; extra outer retries multiply load. [D1 retries](https://developers.cloudflare.com/d1/best-practices/retry-queries/). For notifications preserve the accepted bounded at-least-once tradeoff and operator visibility; provider acceptance is distinct from delivery. A `waitUntil` first-send optimization cannot replace the durable outbox/retry sweep. N:`notifications.md`, “The design under test” and “Findings for GRS-137”; [Workers context](https://developers.cloudflare.com/workers/runtime-apis/context/).

**Defer until measurements justify them:** read replication and bookmark propagation; cached verification/authorization decisions; Workers traffic splitting; changing the one-client database layout outside the required GRS-95 comparison; extra services such as Queues, Durable Objects, Workflows, KV, Containers or an external database; processing-prompt optimization; cold-storage tiering. The accepted stack and GRS-93/95 already provide enough machinery for the first two clients. D1 read replication requires Sessions/bookmark semantics for sequential reads; it is not a transparent performance switch for revocation/publication paths. [D1 read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/). Retain the scheduled recovery and outbox work already called for by the incoming proofs; this recommendation does not postpone required reliable operation.
