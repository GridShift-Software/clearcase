## Acceptance

- [ ] Model candidate, validation, review and publication states explicitly. Bind approval to immutable case/input/results identities.
- [ ] Publish atomically and idempotently. Reject stale approvals and concurrent conflicting version changes.
- [ ] Audit who approved what and when. Keep the previous publication available for deliberate rollback through the same reviewed path.
- [ ] Clients cannot publish or retrieve drafts. A failed publish leaves the prior publication readable; later automation cannot approve on a human behalf.

## Verification

Report PASS, HOLD or FAIL at the exact reviewed revision. Include commands, exit codes and artifact paths. A skipped check is not a pass. Read the local delivery plan and orchestration protocol before dispatch.

Use an independent reviewer for a gate. For discovery or design, verify the cited source or probe and record unresolved choices. Later-phase implementation requires a concrete test recipe before dispatch.

Metric: Publication switch and rollback latency. Budget: Use CC-15 budgets; clients must never observe a mixed or partially written version.

## Boundaries

Keep RAWS and current production read-only. Do not commit case documents, extracted text or secrets. No Cursor agents; every Opus agent uses high effort. Only the coordinator updates Linear. No deployment, production publication or external messages under this issue without the appropriate execution authority.

Return the branch/worktree, base and head revision, changed paths, accepted criteria, failed or skipped checks, evidence paths and proposed follow-ups. Do not mark the issue Done yourself.
