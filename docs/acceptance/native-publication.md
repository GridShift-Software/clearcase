# Native exact-version sign-off and publication (prepared, unverified)

## Rules enforced

- Every route checks, in this order: same-origin POST, `application/json`, all ports composed (else 503 `publication-unavailable`), case id, verified session of this deployment's client (401), `checkRevocation()` (401), then explicit case `publish` authority from the injected authorizer (uniform 403). Only after that is the bounded body (64 KiB) or any ledger, candidate or pointer state read.
- No authority is inferred from staff, global-admin or client identity. No role, review capability or default is invented.
- A sign-off names the exact identity the human reviewed: candidate, link, submission revision and manifest SHA-256, resultsVersion, package `manifestSha256`, package inputRevision, `diagnosticsSha256`, validator version and snapshot revision. The diagnostics digest accepts the canonical validator's exact `sha256:<64 lowercase hex>` form and legacy bare 64 lowercase hex; identity comparisons remain exact-byte comparisons, so the two forms are not interchangeable. Any difference from the current candidate gives 409 `stale-candidate`.
- Sign-off is refused for a rejected import or any error (never waivable), any required section that is not `valid`, and any required preview that is not `rendered`. The candidate reader supplies facts only. A snapshot with any undocumented key, such as `ready`, is unreadable (503). A request with one is invalid (422).
- Acknowledgements cover exactly the new warnings (warnings minus the case's trusted baseline), each once, each with a non-empty reason. Missing, extra, duplicated or error fingerprints are refused.
- The preparer can approve their own candidate only with `selfApproval: true`, recorded on the sign-off. Anyone else claiming self-approval is refused.
- A sign-off is effective only once its audit event persisted (`recorded` → `audited`). Retrying the same operation settles it. Its original audit envelope is persisted and reused even from a different session.
- Publish checks the candidate for early feedback, then requires the atomic adapter to run fresh session/grant and effective sign-off/candidate checks inside the shared mutation boundary. A changed identity, a newly failed check or a changed new-warning set invalidates the sign-off permanently and refuses the publish (409); a revoked grant returns 403 and a revoked session 401. A stale saved boolean or an ordinary CAS after an unguarded pre-read cannot implement this contract.
- Before mutation, the write-once operation intent pins the exact signed identity, expected pointer, actor and original audit envelope. The adapter atomically stores an operation-bound apply receipt with the pointer CAS. Recovery reconciles that receipt **before** rejudging a pending/failed operation's candidate. Later edits, invalidation or another publication cannot strand the original audit or cause reapplication. Current pointer equality is never proof that this operation applied. An unconfirmed commit returns 503 without claiming that nothing changed.
- Withdrawal requires the same fresh mutation-boundary authority and a CAS on the expected published version. It uses the same receipt/recovery protocol and calls only the publisher's `withdraw`. There is no delete, no rollback by deletion and no user-work or originals call.
- The ledger's triggers refuse every rewrite of bound fields, every delete and every `REPLACE`. The only changes allowed are `recorded` → `audited`, a single invalidation, and the recorded operation transitions.

## Snapshot v2 sign-off and publish (real-export unit U5)

A `CandidateReader` that returns `format: 'clearcase.candidate-snapshot/2'` gets the v2 path below. A v1 snapshot is handled exactly as above, with the same statements, the same 64 KiB bound and the same answers; a v1 ledger never names `pub_signoff_evidence`.

- **Composition.** `signoffEvidence: { reader: d1EvidenceReader(DB), store: d1EvidenceStore(DB) }` on the publication ports (without it a v2 candidate answers 503), and `d1PublicationLedger(DB, { evidence: true })` once migration 0005 is applied (a ledger without it refuses a sign-off that carries evidence, and writes nothing). The publisher needs no option: it guards on the signed identity.
- **Sign-off.** The claimed identity gains one key, `evidenceRoot`, which must be the root the candidate now reports (else 409 `stale-candidate`, `fields` naming `evidenceRoot`). The controller checks the sealed run with U3's `verifyEvidence` (complete, bound to this client, case, results version and manifest, pages and item rows covering each other), reads every warning from the sealed rows and records `warningFingerprints` (all of them) beside the acknowledgements. The sign-off row is inserted first and its `pub_signoff_evidence` row second, in one batch; the evidence row takes its candidate from the sign-off row, so the two cannot name different candidates.
- **Grouped acknowledgements.** `acknowledgements` is a list of `{code, reason, fingerprints[]}`: one reason per group, every fingerprint listed, each warning that needs one in exactly one group, none that does not. A per-warning list on a v2 candidate, or a grouped list on a v1 one, is 422. The body bound for a v2 sign-off is 1 MiB, the size D1 holds in one value, instead of a count; the stored list is one entry per group and reads back as one acknowledgement per fingerprint. `code` is the publisher's label for the group: warning evidence rows carry fingerprints only, so it is recorded and not checked against a row.
- **Publish.** The early answer re-checks the sealed metadata. In the `recheck` made for the commit, immediately before the guarded batch and outside it, the controller recomputes the root from the item rows, 500 per read, and compares it with the signed root; any difference, or a sign-off whose evidence row is missing, names another candidate or another root, invalidates the sign-off and refuses with 409 `signoff-stale`, `reason: 'candidate-changed'`. A read that fails is 503 and invalidates nothing. The recompute is one request, bounded in rows per read but not in CPU (about 37 ms for 4,192 rows locally), so it needs Workers Paid. The recheck hands back the exact `[key, json]` rows it hashed. The pointer write then repeats the metadata check in SQL and compares those rows with the stored ones (chunked `json_each` guards that abort the batch on any difference, never depending on the seal triggers), in the same transaction as the receipt insert, and writes nothing if the run, its root, its count or any row changed after the recheck (`guard-refused` `signoff-stale`). A v2 publish whose recheck returns no rows is refused the same way. The receipt's `signedIdentity.evidence` names the generation and root that were signed.

## Originals evidence and the R2 comparison (real-export unit U8)

A v2 run may hold one `original/<assetId>` item per original: `{kind: 'original', assetId, sha256, size, etag}`, the SHA-256 the build hashed, the size it read and the etag R2 gave on that same read. The kind adds nothing to what blocks a sign-off and nothing to v1.

- **Producer.** `createOriginalsProducer` (`originals-evidence.ts`) is a U3 `EvidenceProducer` over the refs `originalRefs(caseFolder, fileAssets)` gives. A step reads `itemsPerStep` originals at most, `batch` at a time, holding at most `windowBytes` of them; each distinct object is read once. An original that is missing, of another size, of other content, over `maxObjectBytes` or unreadable stops the build with an `OriginalsEvidenceError` (only `storage-unavailable` is worth retrying): a run without it would not cover it. It writes nothing itself, so a boundary item the engine asks for again is only read again; no insert-or-ignore is used, because the 0005 seals refuse a second insert.
- **Composition.** `signoffEvidence.originals = r2OriginalsComparison(BUCKET, { batch, limit })`. `batch` bounds concurrent `head` calls; `limit` bounds the distinct originals one recheck compares (R2 calls are subrequests; size it from the account's limit, not from Workers Free's 10 ms). A run that holds originals and has no comparison answers 503; a run with more originals than `limit` answers 503 `originals-over-limit`. Neither passes unchecked, and neither invalidates the sign-off.
- **Publish.** Inside `recheck`, after the item rows are recomputed, every `original` row is read (500 per read), each distinct object (`orig/<sha256>`) is `head`ed in batches, and its etag and size are compared with the row. A missing object, another etag or another size invalidates the sign-off and refuses with 409 `signoff-stale`, `reason: 'originals-changed'`, before any pointer or receipt is written. A `head` that fails is 503 and invalidates nothing. R2 is outside D1, so this is a read at a point in time, not a lock: an object replaced after the comparison and before the D1 commit is not seen (the same window the Clerk recheck has). A content-addressed original is never meant to be rewritten, and the same bytes written again are refused too, since the etag is what was sealed.
- **Not changed.** `publication-material.ts` and `original-facts.ts` still hash every original for a v1 candidate, exactly as before.

## Remaining integration boundaries

- Alpha policy explicitly uses the case `publish` grant for sign-off and publication; no separate review-role decision blocks this component.
- The audit event is appended after the pointer applies, and a failed append returns 503 until a retry settles it from its receipt and stored envelope. Real audit durability and eventId deduplication are unverified.
- The required atomic adapter and durable apply-receipt store are typed but not implemented against GRS-114/115. The test-only publisher models serialization and receipts in memory; that is not durable or provider evidence.
