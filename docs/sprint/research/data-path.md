## 1. Today's path

**The v5 export.** One workspace HTML (generation `v5-workspace-html`) holding four JS roots (`DATA`, `META`, `window.__SCHED__`, `window.__CASELINES_IDX__`), beside a case folder. The fixture folder (`.local/v5-verification.json` → `fixtures/v5-002/tree`) has 1,753 files, 3.26 GB on disk, 1.85 GB of unique referenced bytes: 1,161 PDF, 467 `.eml`, 91 `.msg`, 15 Word, 13 JPEG, 2 HTML, 1 XLSX, 1 TXT, 2 with odd extensions. 117 files are over 2 MiB, 35 over 16 MiB, 17 over 32 MiB and 7 over 100 MB (the largest is 258 MB; all seven are large court-filed bundles).

**`convert`** (`bun scripts/case-package/cli.ts convert --html --case-folder --case-id --out`, `src/lib/case-package/v5/adapter.ts`, `writer.ts`) never executes the HTML: it slices the four roots, splits them into 35 dataset envelopes (`datasets/<key>.json`, `v5.<key>@1`, data unchanged, canonical key order), writes `assets.json` and a closed `manifest.json`, then validates in full against the case folder. Package: 37 files, 6.2 MB, largest 1.8 MB. Assets: 3,054 keys = 1,689 register refs + 57 package files (`P-<16 hex>`, bundle and schedule PDFs) + 1,308 `embedded` e-mail attachments without their own bytes. 67 sha256 values are shared by more than one ref. Identity: `resultsVersion = sha256(format, caseId, inputRevisionId, files[])`, `manifestSha256` beside it. Known v5 warnings: two META count disagreements, `ASSET_MISSING_AT_BUILD` for the originals the folder lacks, case-mismatch folds.

**Read model.** `project(candidate, counts)` in `src/lib/local-case/project.server.ts` turns `readCandidate()` into `{documents[] (ref, ord, row_json, state_json, attachments_json), assets[], seeds[], chronologyJson, overview, expect}`; `readModelDigest` seals it. The hosted `StagedProjection` (`src/lib/results/hosted/read-model.ts`) is the same shape, built by `preparePackage(files).project(facts)` from stored originals' facts instead of the folder.

**Local import and serving.** `service.server.ts` runs `importCandidate` (strict JSON, schemas, bounds, streams every referenced original once at 1 MiB chunks, 120 s deadline), stores package bytes and the projection in `node:sqlite` (`version`, `package_file`, `document`, `asset`, `seed`; user work in `work.*`), then `activate` re-imports from the stored bytes and refuses if the digest moved. 29 s for v5. Every page's `+layout.server.ts` calls `a.verify(v.id)`, which re-hashes the read model. Views read rows from `CaseStore`; originals are served from the case folder through the local originals site and the pdf.js host in `src/lib/local-case/viewer/`. Embedded attachments resolve to `route: 'parent'`: open the container (`.eml` is `text-sandboxed`, `.msg` is `download`).

**Hosted today and where it fails.**
- *Intake* (`storage/cloud/intake.ts`): one declared/stored/finalized row per file, write-once `orig/<sha256>`, finalize re-reads and hashes the whole object in a 128 MB Worker, so `maxOriginalBytes = maxBufferedObjectBytes`, set to 16 MiB in B's deployment policy. 1,140 of 1,753 originals uploaded; 613 never did (`handoff-spindown-20261027.md`). The seed-kit package built against that subset carries 606 `missing` assets. Intake measured at about 14 s per file, 62 minutes in total.
- *Staged import* (`stepped-stager.ts`, `candidate-stager.ts`): leases and epochs in `native_import_stage_run`, bounded steps, `STAGED_WORK_CAP`, deployment `storageBudgets`/`importBudget` (`maxDocuments` 4,096, `maxRowsPerBatch` 100, `maxVerifyBytes` 256 MiB). 49 minutes for v5. Package bounds are 8,192 files, 64 MiB per file, 2 GiB total.
- *Evidence engine* (`publication/hosted/evidence-build.ts`, `pub_evidence_*`, `evidence-gate.ts`, Browser Rendering): renders every PDF; `pdfEvidenceBudget.maxFileBytes` (16 MiB) seals a bigger PDF as a `failed` preview, which blocks sign-off (`rules.ts` `preview-not-ready`); a cited missing original is `failed` too; `required-section-render.ts` proves only the chronology page, so clients saw only the chronology.
- *Reads*: `loadVerifiedModel` loads every `rs_document`, `rs_asset`, `rs_seed` row and re-hashes per isolate; `verifiedRead` hashes whole objects; search 503.
- *Publication*: `pub_signoff` binds `results_version`, `manifest_sha256`, `diagnostics_sha256`, `validator_version`, fingerprints and acknowledgements, with the evidence root (`0004_publication_evidence.sql`); `d1-publisher.ts` recomputes the root and flips `rs_publication (case_id → version_id, previous_version_id)` in one batch.

## 2. The demo path (v5 on staging by Monday)

Minimum steps, in order:
1. On the operator machine, `convert` the real HTML against the full case folder (not the 1,140-file subset); keep the package directory and the `--report`. Expect only the folder's genuine missing originals plus the two META disagreements as warnings.
2. **Shard builder** (`scripts/publish/build-view-payloads.ts`, Bun). Inputs: the package directory, the case folder (or the report proving it was validated there), `caseId`, hosted route prefix. Outputs under one prefix, say `views/<rvHex>/`: `manifest.json` (resultsVersion, manifestSha256, readModelDigest, validatorVersion, diagnosticsSha256, warning fingerprints, counts, and `sha256` plus size per shard), `view/<key>.json` for each dataset view (envelope data + the resolved ref set + its `view-content` fields), `list/page-<n>.json` and `list/facets.json` for chronology and documents, `doc/<ref>.json` (row, state, attachments, original pointer), `search/index.json`, and `originals.json` (asset key → sha256, size, mediaType, display filename, parent). Every object `Cache-Control: public, max-age=31536000, immutable`, ETag = shard sha. Reuse: `importCandidate` → `Candidate`; `readCandidate`; `project` (local) or `preparePackage(...).project(facts)` with facts read from the report; `readModelDigest`; `canonicalJson`; `readViewContent`; `verifyCandidateBytes` for the stored package copy; `datasetOf`/`viewContentOf` logic from `local-case/results.server.ts` for per-view shaping.
3. **Originals to R2 with rclone** over the S3 API from a builder-emitted manifest `path → sha256, size`: only referenced originals (about 1,744 file assets, 1.85 GB), key `orig/<sha256>` (the existing `originalKey`, no 2-char prefix) so the deployed viewer route and `rs_original.object_key` still agree; `rclone check` afterwards. Also upload the package files to `pkg/<rvHex>/<sha256>` so operator verify (`verifyCandidateBytes`) keeps working.
4. **D1 rows** (one script, `wrangler d1 execute` or the Worker's operator route): `rs_case`; `rs_results_version` with `state='stored'`, every expected count, `read_model_sha256`, `overview`, `package_bytes`, `import_seq`; `rs_package_file`; `rs_original` + `rs_case_original` (asset_id = the asset key) for every uploaded original so `assets.ts` can locate them; `rs_document`/`rs_asset`/`rs_seed` only if the notes, registers and `original-attribution` paths still read them (they do today). A new `rs_shard_manifest(version_id, prefix, manifest_sha256)` or a KV key holds the shard root.
5. **Sign-off and publish.** The human signs a record binding `resultsVersion`, `manifestSha256`, shard `manifest.json` sha256, `validatorVersion`, `diagnosticsSha256`, acknowledged fingerprints (missing originals, META disagreements, case-mismatch) and the signer. Publication writes `rs_publication` and the KV pointer in one step; readiness (`readiness.ts`, `rules.ts`) treats a failed or absent preview as a warning and "required render" as "shard manifest present and hashed" (S4 rule change, ADR 0010/0013 amendment to record).

Decisions a builder must not guess: shard prefix and page size (200 or 500 rows); whether the shard root lives in a D1 table or KV; whether `rs_document`/`rs_asset`/`rs_seed` are still written (notes anchor on refs and `childDocuments` read them); whether sign-off reuses `pub_signoff` (it demands `candidate_id`, `link_id`, submission ids that no submission produced) or a lean new table; how the viewer resolves an original (by `asset_id` = ref, as today, or by sha256 straight from `originals.json`); the presigned-download threshold (about 100 MB) and whether the 57 package-file PDFs are offered at all; what `doc/<ref>` says for the 1,308 embedded attachments (open container only); whether staging keeps the real case label; and who holds the R2 S3 token and Clerk staging keys.

## 3. The post-demo path (14–17 TB client)

**Per batch the Spark pipeline emits** one sealed `bundle.json`: batch id, case id, parent batch id, pipeline version, and every part's path, size and sha256, plus counts and attested receipts (page count per PDF, render check, META reconciliation, text extraction status). Parts: `catalogue/<n>.ndjson` (one row per kept file after de-NIST and dedupe: sha256, size, relative path, display name, custodian, media family, parent sha256 for extracted attachments, batch id, text status, page count, duplicate paths), `datasets/<key>/<part>.json` (same envelope schema as today, sharded), `text/<sha256>.zst`, `prev/<sha256>.pdf` for every non-PDF kept file (processing contract: previews and extracted attachments become mandatory, not producer-optional), and the read-model shards themselves, built on the Spark side with the same builder as step 2. rclone moves originals and parts; one Worker call with the manifest sha256 starts a Workflow that streams and hashes each part and loads catalogue rows in 2,000-row steps.

**Appending batch N+1.** Catalogue rows are append-only with `batch_id`; a published version is a version row plus the set of batch ids and the shard prefix for that version. Shards are per version and never rewritten; the pointer flips only after the new version's shards and rows exist, and no object a published version references is deleted. Refs must be stable: today a ref is a package-local alias (`results-package.md`, Identity), which breaks the moment two batches exist. The pipeline must own ref allocation (a registry keyed by sha256 and parent, carried from batch to batch) and the contract must say so; `project` and the shards then keep `doc/<ref>` stable. Reprocessing is a new version, never an edit (ADR 0010).

**Format changes.** A `formatVersion 2`: `files[]` becomes a manifest of parts (dataset key + part ordinal), `assets.json` becomes catalogue NDJSON parts, and the bounds move from 8,192 files / 64 MiB per file / 2 GiB total / 500,000 assets / 32 GiB of originals to "64 MiB per part, unbounded parts, unbounded totals, 8 GiB per original". Validation stops hashing every original on import (rclone receipts and R2's stored sha256 replace it) and the required-dataset rule pages over parts. The chronology stays required but is paged. **Processing contract amendments:** batch manifest and receipts; previews and extracted attachments mandatory; sha256-anchored stable refs across batches; page citations verified against the shipped preview bytes on the Spark; catalogue rows as a producer output; the dedupe table as provenance.

## 5. Risks and mitigations

- **Missing originals.** The full-folder convert should show only the folder's genuine missing files; acknowledge them at sign-off with a reason and show "Original not supplied" on the document page. Converting against a partial upload (as on B) produces hundreds of `missing` assets, so never build shards from a subset.
- **Embedded e-mail previews.** 1,308 `embedded` assets have no bytes; the document page can only open the container. `.eml` renders text-sandboxed, `.msg` is download-only. For the demo, say so in the attachment list; for the client, make extraction and PDF previews mandatory in the contract.
- **Files over 100 MB.** Seven PDFs, up to 258 MB. Range streaming with `onlyIf` etag (S2) for in-app viewing; downloads over about 100 MB through presigned R2 URLs; rclone with multipart (`--s3-chunk-size 64M`) for the upload. No whole-object hash in the Worker, ever.
- **Non-PDF formats.** 467 `.eml`, 91 `.msg`, 15 Word, 1 XLSX, 2 HTML, 13 JPEG. Images and `.eml` open in the viewer; the rest are downloads. Mark them `downloadOnly` in `originals.json`; for the client, converted previews from the Spark.
- **Identity drift.** If the shard manifest is not bound into the sign-off, the human approves something other than what clients read. Bind it, and make publication recompute the manifest sha before flipping.
- **Case-mismatch and shared sha256.** 67 refs share bytes and some paths fold case-insensitively; key by sha256 and keep ref → sha256 in the catalogue so dedupe is free and a retry is idempotent.

Map notes: the 16 MiB cap is a deployment policy value (`intakeBudget.maxFileBytes`, `storageBudgets.maxOriginalBytes`, `pdfEvidenceBudget.maxFileBytes`), not a code constant; `docs/acceptance/native-staged-import.md` "The reviewed ceiling" holds the real B numbers. The seed kits under `.local/v5-live-seed-kit/` were built against the 1,140-file subset. `src/lib/views/payloads.ts` and `scripts/publish/` do not exist yet on the sprint branch.
